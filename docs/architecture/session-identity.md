# Идентичность сессии

Программа вне ccmux встречает сессию по одному из её имён: по заголовку окна или панели, по
идентификатору, который провайдер дал разговору, или по адресу. `ccmux whois` отвечает на любое
из них одной формой — `SessionIdentity`: что это за сессия, где её папка, какому репозиторию папка
принадлежит, какой проект этот репозиторий называет своим и под какими идентификаторами провайдера сессия жила.

Реализация: `src/session/identitySchema.ts` (форма ответа), `src/session/identity.ts` (сборка),
`src/session/whois.ts` (разбор вопроса и сопоставление), `src/session/repository.ts` (репозиторий
и проект папки), `src/commands/whois.ts` (CLI, флот, поток).

## Что входит в идентичность

| поле | откуда |
|---|---|
| `address`, `machine`, `name`, `provider`, `archived` | реестр сессий |
| `title` | имя, под которым сессия запускается (`<rcPrefix>-<имя без cc->`); его провайдер показывает в заголовке окна |
| `dir` | зарегистрированная рабочая папка, на машине самой сессии |
| `repository` | `owner/name` из адреса `origin` этой папки; `null`, если папки нет, она не checkout или у неё нет `origin` |
| `project` | проект, к которому репозитории относят эту папку своими объявлениями в `.passport.json` — правила ниже; поля нет, когда никто его не объявил или объявления расходятся |
| `checkouts` | checkout проекта на машине сессии: папка, репозиторий, роль и признак «сессия здесь»; есть вместе с `project` |
| `running` | последнее наблюдение демона; `null`, когда демон не запущен |
| `conversation` | идентификатор провайдера, который сессия читает сейчас |
| `conversations` | все идентификаторы за жизнь сессии, от старого к новому, с временем первой и последней записи |
| `createdAt`, `lastActivityAt` | первая запись самого старого разговора и последняя запись любого |

**Репозиторий отвечает «где», проект — «чей».** Публичный исходник продукта, его приватная рабочая
половина и компаньоны — разные репозитории одного проекта, и сказать это могут только сами
репозитории. Считаются два объявления, оба в `.passport.json` в корне checkout (ближайший вверх от
папки сессии каталог с `.git`, со снятыми ссылками):

- собственное `identity.project` этого checkout;
- если его нет — checkout рядом, в том же родительском каталоге, чьё объявление называет этот
  репозиторий своим источником (`source.repositoryId`) и несёт `identity.project`. Публичный и
  клиентский исходник о своей рабочей половине молчат, поэтому за пару говорит половина. Репозиторий
  исходника для сравнения — `identity.repositoryId` его объявления, а без него `owner/name` из
  `origin`; регистр не различается.

Папка, которая сама не лежит в checkout, но содержит их, — каталог, где сидят половины продукта, —
принадлежит проекту, к которому сводится каждый checkout в ней, и никакому, если хоть один сводится
к другому или ни к какому. Репозитория у такой папки нет.

Ключ проекта отдаётся ровно как записан; значение с косой чертой, пустое или длиннее 200 знаков
проектом не считается — так же его отвергает формат объявления. Имя репозитория или папки проектом
не становится: сосед с именем `<имя>-dev`, который ничего не объявляет, ничьей половиной не
является. Два соседа, называющие разные проекты, не дают ни одного. Поле `project` тогда
отсутствует.

Репозиторий без единого объявления остаётся без проекта: он сам себе продукт, и его ключ —
`repository`. Сводится только то, что видно из одной папки: соседи одного родительского каталога и
прямые дети папки сессии, не глубже. Проверяется ключ проекта, а не объявление целиком: каталог
продуктов с ролями половин и отказом неверному объявлению ведёт не ccmux. Проект определяет машина, на которой лежит папка: вопрос к флоту приносит его вместе
с остальным ответом.

Ответы о папке помнятся по файлам и сбрасываются, когда файл меняется, — одно правило для
`origin` (по `.git/config`), объявления и списка соседей. Поток поэтому сообщает о сессии заново,
когда к checkout добавили `origin`, переписали объявление или рядом появилась половина.

Ничего нового ради этого ответа не записывается. Реестр хранит один идентификатор — текущий, и
журнала прежних нет: он был бы верен только с дня своего появления. Прежние жизни сессии читаются
из хранилища провайдера.

## Жизни сессии

Claude Code не держит один идентификатор на всю жизнь сессии: `/clear`, форк при переполнении
контекста и сжатие начинают новый файл под новым идентификатором. Каждый такой файл открывается
записью `custom-title` с именем, под которым сессия запущена, — той же меткой, по которой демон
[следует за форком](follow-the-fork.md). Жизнь сессии — файл `<uuid>.jsonl` в её проектной папке,
который открывается её заголовком.

Три ограждения, каждое в пользу «не приписать»:

- идентификатор, который сейчас читает другая сессия, принадлежит ей, каким бы заголовком ни
  открывался файл;
- заголовок, общий для двух сессий одной папки (`cc-x` и `x` запускаются под одним), не даёт
  прежних файлов ни одной из них — остаётся только текущий идентификатор;
- файл без заголовка (разговор, начатый руками) и файл с заголовком удалённой сессии — ничьи.

У Codex и OpenCode идентификатор один на всю жизнь сессии, и список состоит из него.

## Вопрос и сопоставление

Вопрос — одна строка, и каждый её вид сопоставляется точно:

- **идентификатор провайдера** (UUID или `ses_…`) — с любым идентификатором из `conversations`,
  текущим или прежним;
- **адрес** `<машина>:<имя>` — спрашивается только названная машина;
- **слова** — заголовок окна или голое имя. Заголовок делится по пробелам, и сессия найдена, когда
  одно из слов целиком равно её `title`. Префикс, более длинное имя и похожее имя совпадением не
  являются: ближайшая по имени сессия — другая сессия, и работа, отнесённая к ней, отнесена
  неверно без единого признака ошибки.

Поле `found` называет исход: `session` — ровно одна сессия; `ambiguous` — вопрос подходит
нескольким, все они в `candidates`, ни одна не выбрана (голое имя, которое есть на двух машинах);
`conversation` — идентификатор, который не читает и не читала ни одна сессия: ответ говорит, на
какой машине лежит разговор, каким адресом `ccmux transcript` его открывает, в какой папке он шёл
и каким заголовком открывается; `none` — ничего.

## Флот

Каждая машина отвечает за свои сессии: только она читает свой реестр и файлы провайдера рядом с
ним. Команда спрашивает каждую (`whois --local --json`) и складывает ответы; `machines` называет
спрошенные и те, что не ответили, с причиной. Ответ, в котором названа другая машина, чем
спрошенная, ответом этой машины не считается. Exit 0 — найдена сессия или разговор, 1 — не сессия
или неоднозначно, 2 — не найдено, и при этом какая-то машина не была спрошена.

`whois --all` отдаёт все сессии флота той же формой.

## Поток изменений

`whois --follow` — идентичности сессий этой машины по мере изменения, NDJSON:

- `{"event":"session","session":{…}}` — сессия, как она есть сейчас. Каждая приходит один раз при
  открытии потока, поэтому отдельного первого чтения не нужно и между ним и потоком нельзя
  провалиться; затем — снова, когда меняется что-либо, кроме времён активности: папка, репозиторий, проект,
  идентификатор провайдера, запущена ли она, архив;
- `{"event":"gone","address":…}` — сессия ушла из реестра.

Времена активности в сравнение не входят: они двигаются с каждым сообщением, и поток стал бы
лентой «кто занят», которой уже служит [лента событий](session-events.md). Новое значение они
получают в очередной строке `session`.

Изменения замечаются по двум файлам, которые их записывают, — реестру и inventory демона; каталог
состояния наблюдается целиком, потому что оба файла заменяются переименованием. Под наблюдением
идёт редкое перечитывание (30 с): потерянное файловое событие иначе оставило бы потребителя со
старой папкой или идентификатором без единого исправления. Прочитанное из файлов разговоров
хранится, пока файл не изменился, и повторный проход по неизменному хранилищу файлов не читает.

### Поток по флоту

Поток ведёт все машины флота; `--local` оставляет одну. Свою машину он наблюдает по файлам, как
описано выше. Каждую другую спрашивает заново через 15 секунд после её прошлого ответа — у её
демона, по изменению (`_peer-read identities`): строки, которые читатель уже держит, возвращаются
отпечатком, а демон отвечает из прогретого чтения файлов разговоров. Следующий вопрос машине
уходит только после ответа на предыдущий, поэтому медленная машина спрашивается реже и никогда —
дважды сразу.

Третья строка потока — `{"event":"machine","machine":…,"status":"asked"}` либо
`{"status":"unavailable","error":…}`. Она приходит после первых строк `session` этой машины и
значит «машина прочитана»; затем — только когда состояние машины или причина меняется. Сессии машины, которая
перестала отвечать, ушедшими не объявляются: их не смотрели. Что ушло за время её молчания,
сообщается, когда она ответит снова. Сессия различается адресом: одинаковые имена на двух машинах —
две сессии.

Машина, чей ccmux или демон старше этого вопроса, называется `unavailable` с причиной, а не
опрашивается обходным путём. Машина без запущенного демона отвечает тем же ответом, собранным
самой командой. Вопрос, который ещё в пути, когда поток останавливают, обрывается вместе с ним. Состав флота читается при открытии потока.

## Где остальной проект

Сессия сидит в одном checkout — обычно в исходнике продукта, — а очередь задач и рабочие правила
продукта лежат в приватной половине рядом. Какая это папка, сессии больше неоткуда узнать: те же
объявления, что называют проект, называют и его checkout. `checkouts` — это checkout в одном
каталоге (рядом с checkout сессии либо внутри папки, на которой она открыта), которые сводятся к
тому же проекту. Роль — `identity.role` объявления; без неё `private-workspace` у checkout, который
называет свой источник, и `source` у остальных. В ответах поиска поля нет: строка называет свою
папку, а не соседние.

Изнутри сессии `ccmux whois` без аргумента отвечает о ней самой — по `CCMUX_SESSION`, только на
своей машине. Так агент находит рабочую половину, не обращаясь к реестру проектов.

## Свой адрес в окружении

Процесс внутри управляемой сессии узнаёт, кто он, из окружения: `CCMUX_SESSION` — имя сессии на её
машине, `CCMUX_ADDRESS` — `<машина>:<имя>`, тот же ключ, что в `address` выше и в `ccmux fleet`.
Программа, которая подписывает свою работу сессией, берёт адрес отсюда и не собирает его из имени
хоста: имя хоста не равно имени машины во флоте. Заголовок окна — третье имя той же сессии
(`title`), и по нему её находит `whois`.

Все три переменные идентичности (имя, адрес и chat-capability) ставит одна функция,
`src/agent/launch/identityEnv.ts`, для каждого провайдера, предварительно убрав унаследованные:
супервизор, запущенный из управляемой сессии, несёт её идентичность, и следующей сессии она не
достаётся. Сессия, запущенная до появления `CCMUX_ADDRESS`, показывает пометку `env` в
`list`/`fleet` до своего рестарта; сам рестарт ccmux не делает.

## Схема

`whois --schema` печатает JSON Schema трёх ответов (`answer`, `list`, `event`), построенную из тех
же Zod-схем, которыми ответы проверяются между машинами. Потребитель читает по схеме и не разбирает
вывод для человека.

## Реплики человека по сессиям

Выгрузка сказанного — режим [поиска по всем разговорам](transcript-adapters.md), а не второй
читатель хранилища: `search --role user --since 1d --json --full --limit 100000` отдаёт каждую
реплику человека за сутки по флоту с её временем и целым текстом. У каждой строки и разговора —
`machine`, `address`, `dir`, `repository`, `project` (то же поле и то же правило, что у сессии) и
`ofSession`: сессия, которой разговор принадлежит или принадлежал, по тем же правилам, что и жизни
сессии выше. `session` остаётся ответом на другой вопрос — кто читает этот разговор сейчас.

## Куда попало сообщение с меткой

Программа, которая вставляет человеку в сессию сообщение со своей меткой — идентификатором записи,
номером заявки, — узнаёт, какая сессия его получила, не по заголовку окна, а по самому сообщению:
`search PATTERN --receipts --json` отдаёт `receipts.marks` — по одной записи на каждое разное
значение, которое нашёл шаблон (первая скобочная группа, а без групп всё совпадение), и в ней
`deliveries`: разговоры, где оно есть, с теми же полями принадлежности, строкой `seq`, ролью,
`messageId` и `receivedAt` — временем первого сообщения с меткой в этом разговоре. `--limit` на
квитанции не действует; разных меток не больше 10 000 на машину, и `truncated` говорит, что их было
больше. Сессия Claude, продолженная в новом файле, несёт копии прежних сообщений под их же id — такая
копия считается той же доставкой и остаётся за разговором, который сессия читает сейчас. Ничто
другое копией не считается: у Codex id сообщения — номер строки файла. Адрес сессии-получателя —
`machine` и `ofSession` доставки; `ofSession: null` значит, что разговор не принадлежит ни одной
управляемой сессии. Метка,
встретившаяся в двух сессиях, — две доставки: выбор между ними остаётся потребителю.
