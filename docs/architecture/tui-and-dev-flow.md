# TUI (Ink) и dev-флоу

## Что это
`stitchmux` без аргументов на TTY → интерактивный терминальный UI на **Ink** (React → Yoga →
ANSI; тот же класс, что Claude Code). Категория — **inline-native** по умолчанию (живёт в
потоке терминала, остаётся в истории), **fullscreen** по флагу (`-f`, alt-screen + листаемый
транскрипт справа). Клавиша `f` переключает на лету.

Структура — `src/tui/` (DRY: общие `format`/`components`/`hooks`, два `views/` отличаются
только layout-обёрткой). Подробности компонентов — в коде.

## Dev / Prod / self-update
Bun-stitchmux **заменил** bash-stitchmux локально (bash-демон убит, плист `.legacy`, бинарь → `stitchmux-legacy`
как fallback). Два режима, **развязаны** — правка дев-исходника НЕ трогает прод-демон, который рулит
боевыми сессиями:

| Режим | Команда | Что запускает |
|---|---|---|
| **DEV** | `stitchmux-dev` | `bun run <repo>/src/cli.ts` (исходник, `bun tui:hot` = `--hot` для HMR) — разработка |
| **PROD** | `stitchmux` | `bun ~/.stitchmux/app/stitchmux.js` (бандл ~1.7МБ) — боевой; демон `com.stitchmux.daemon` крутит ЕГО |

Лаунчеры: `~/.local/bin/stitchmux-dev` → исходник; `~/.local/bin/stitchmux` → бандл.

**Инвариант: ОДИН демон (прод).** Дев демон НЕ ставит → нет коллизии двух ensure-циклов (делить
реестр двум демонам нельзя — был реальный баг: bash+наш писали разный формат → мусорные сессии).
Оба режима читают один `~/.stitchmux-sessions` (JSONL Session-schema) — чтение из обоих безопасно.

### Бандл + self-update
- **Сборка** — dev-скрипты в `package.json` (НЕ команды тулзы — `stitchmux` их не содержит, в клиентский
  бандл они не попадают): `bun run stage` → `bun build --target=bun --external react-devtools-core` →
  `~/.stitchmux/staged/stitchmux.js` (для локального теста апдейта). Логика — `scripts/release.ts`.
  (`react-devtools-core` external: Ink тянет его только в СВОЁМ dev-режиме, в проде не нужен.)
- **Апдейт**: `stitchmux update` — **локальный staged ПЕРВЫМ** (тестим сборку локально), иначе remote: `release.json` —
  подписанный Ed25519 `CliBuildManifest` (ключ в `src/release/trust.ts`, закрытый — секрет CI
  `STITCHMUX_RELEASE_SIGNING_KEY`; плоские `version`/`url`/`sha256` — для прежних stitchmux и `install.sh`) →
  подпись до скачивания → `applyCliUpdate` stitchkit (только https и публичные хосты, если нет
  `releaseAllowPrivateHosts`; лимиты размера и времени; кандидат запускается `bun <кандидат> version` ДО подмены).
  Atomic swap `~/.stitchmux/app/stitchmux.js` (+`.bak` и его digest `.bak.sha256`) → bounce демона (`kickstart -k`). **Сессии переживают** (tmux
  независим от демона); каждый `_run` подхватывает новый код на следующем рестарте. Откат: `stitchmux update --rollback` (`rollbackCliUpdate` сверяет `.bak` с записанным digest).
- Версия — в шапке TUI (`stitchmux vX.Y.Z · fleet`). Пути: `src/config/paths.ts`. SELF_ARGV (`src/util/env.ts`)
  различает compiled-бинарь / dev-исходник / bundle → плист печёт `bun ~/.stitchmux/app/stitchmux.js daemon`.

### Раздача на флот (GitHub Releases, без своего бэкенда)
Monitoring consumers use the resident [status snapshot](monitoring-status.md), not repeated
list aggregation. It is produced by the existing daemon observation loop.

- **Инварианты релиза**: релиз рождается ТОЛЬКО из тега в CI; тег стоит ровно на коммите
  с этим кодом (`git diff vA..vB` = что вошло); красный check = релиза физически нет;
  локального publish-пути не существует.
- **Церемония** — `bun run release X.Y.Z "notes"` (`scripts/release.ts`; НЕ команда тулзы —
  только из репо, у клиента нет ни репо, ни package.json). Локально ТОЛЬКО git-часть:
  отказ при грязном дереве / не-main / существующем теге → прегейт `bun run check` → бамп
  `package.json` → перенос `[Unreleased]`-секции CHANGELOG в датированную `[X.Y.Z]` →
  коммит `X.Y.Z: notes` → тег `vX.Y.Z` → push. Та же церемония разрезана на две половины для
  проводника, который гоняет check между ними и сообщает каждый шаг: `--commit X.Y.Z "notes"`
  (бамп + CHANGELOG → локальный коммит) и `--tag X.Y.Z` (HEAD объявляет версию и несёт её
  секцию CHANGELOG → тег → push). Одноразовая команда — их композиция вокруг check. `--tag` (а значит и церемония) отказывает без `STITCHMUX_RELEASE_RECORDED=1`: эту переменную ставит только проводник, записывающий каждый выпуск в журнал публикаций; тег, отправленный вручную, выпустил бы релиз без записи.
- **Проверки тега.** В `.github/workflows/ci.yml` задачи `ci`, `smoke` и `darwin-native`
  проверяют исходники, установленный SDK, запуск бандла и нативный компонент. Версия тега
  должна совпасть с `package.json`. Команда `--ci-assets` подписывает манифест с версионным URL.
- **Публикация SDK.** Job `release` устанавливает собранный архив в чистый проект и прикладывает
  его к черновику GitHub. Job `publish-sdk` получает этот же архив по ID артефакта и SHA-256.
  В настройках npm доверенный издатель пакета `@stitchmux/client` соответствует
  репозиторию `max-listov/stitchmux`, workflow `ci.yml` и окружению `npm-production`.
  Официальный npm CLI публикует архив через OIDC с provenance. Повтор сверяет уже доступные
  байты этой версии. Установка по версии из публичного npm проходит оба typecheck и runtime-проверку.
- **Публикация на флот.** Job `activate` сверяет commit черновика и SHA-256 его SDK с проверенным
  архивом, затем открывает GitHub Release. При повторе можно продолжить черновик того же commit.
  Опубликованная версия иммутабельна.
- **Подписка флота**: машины ставят `releaseUrl = .../releases/latest/download/release.json` +
  `autoUpdate:true`. Демон каждые `updateCheckInterval` (деф. 300с; серверам ставим 60с) сравнивает
  semver, тянет, **sha256-verify → preflight → swap**. Анонимный HTTPS + CDN GitHub, токены не нужны.
  Сам демон берёт релиз, только когда тот отлежался: `releasedAt` из `release.json` старше
  `autoUpdateSettleSeconds` (деф. 600с) — это время, которое релиз живёт на первой машине один.
  `stitchmux update` руками берёт сразу; пропавший с диска бандл восстанавливается без выдержки.
- **Защита от кривого релиза, 2 слоя** (`update.ts` + `util/bootGuard.ts`): (1) **preflight** —
  `bun <candidate> version` обязан вернуть верную версию ДО свапа (ловит не-загружающийся бандл,
  live не трогается); (2) **boot-guard** — счётчик стартов демона (`~/.stitchmux/boot-attempts`):
  3 старта без успешного ensure-тика → возврат `.bak` + exit≠0 → boot-юнит поднимает старый бандл.
  Первый хороший тик чистит счётчик и записывает sha256 бандла как проверенный
  (`boot-attempts.proven`). Цикл падений на проверенном бандле — причина вне бандла (lock после
  аварии, диск, зависимость): `.bak` не копируется, рестарты супервизора продолжаются. Откат
  вручную: `stitchmux update --rollback`.
- **Супервизор не сдаётся**: systemd-юнит — `StartLimitIntervalSec=0`, `Restart=always`,
  `RestartSec=15`. Предел запусков у systemd терминален, и его бюджет тратят старты юнитов с
  `Requires=stitchmux.service`: зацикленный соседний адаптер съел половину бюджета, пока демон падал на
  lock. launchd (`KeepAlive`) тоже не сдаётся.
- **Юнит сводит только установленное приложение**: на старте демон переписывает уже
  установленный boot-юнит под определение своей версии (`convergeBootUnit`), но только когда он
  сам — установка по умолчанию: бандл, данные в каталоге по умолчанию (`ownsInstallation`, то же
  условие охраняет PATH-шим). Демон из временного каталога (тест) или из исходников (`stitchmux-dev`)
  юнит не трогает: иначе он направил бы `ExecStart` на свой бандл. Так полный прогон тестов под
  root на Linux однажды переписал боевой `stitchmux.service`, и следующий рестарт не нашёл бандл.
  Тестовые машины носят метку `stitchmux-test.service`, не боевую.
- **Новый клиент** — одной командой: `curl -fsSL <repo>/releases/latest/download/install.sh | bash`
  (`scripts/install.sh`): ставит bun при отсутствии, качает бандл + sha256-verify, шим в `~/.local/bin/stitchmux`,
  `stitchmux install --rc-prefix … --release-url <manifest>` (пишет releaseUrl + autoUpdate). Override
  источника: `STITCHMUX_REPO=owner/name`.

### Системный лог (`~/.stitchmux/stitchmux.log`)
JSON-строки, уровни `debug<info<warn<error`, порог `logLevel` в machine.json (деф. `info`, демон
перечитывает живьём — флипнуть в `debug` без рестарта). Ротация по размеру (5MB × 3 ≈ 15MB cap,
фикс — не конфиг, чтобы лог не съел диск сервера). События: daemon up/stop, heal (сессия упала→рестарт),
session new/start/stop/rm, update seen/applied/failed/rolled-back, boot-guard revert. `src/util/log.ts`.

### Код возврата команды — ответ на вопрос об адресе

Любая команда, адресованная сессии, сперва проверяет, есть ли такое имя в реестре, и только потом
смотрит на состояние. Промах по имени — ненулевой код и строка `unknown session: <name>`; состояние
(«не запущена», «нет живого пейна», «уже снята») — отдельный ответ, и оно может быть нулём.
Разделение важно потому, что опечатка в адресе — самая частая ошибка, а фразы вида «not running» и
«nothing to capture» истинны для остановленной сессии и ложны для несуществующей: потребитель,
судящий по коду, получал «сделано» на промах. Проверка вердикта для каждого такого глагола —
`test/unknown-session-verdict.test.ts`; новый глагол добавляется туда строкой.

Брошенная команда печатает ОДНО предложение, а стек уходит в лог: иначе рантайм выводит вырезку
собранного бандла — номера строк за сорок тысяч и кусок постороннего хелпера — туда, где человек
ждёт причину (`src/cli.ts`).

## Реальные данные
`stitchmux` (бандл) и `stitchmux-dev` (исходник) читают живой `~/.stitchmux-sessions` — это не мок.
`rcPrefix` дефолтится в `local` (свежая машина без `machine.json` просто работает; `install`
пишет реальный local|dev|prod). Изоляция dev-реестра при нужде — `STITCHMUX_SESSIONS=…`.

## Правки → проверка
Hot-reload:
- **TUI** — `bun tui:hot` = `bun --hot src/cli.ts` — Bun перезагружает модули на изменение (для TUI
  экспериментально: raw-mode может мигнуть; если глючит — обычный рестарт).
- **Dev-демон** (изолированный dev-инстанс, см. DevPattern) — `bun daemon:watch` =
  `bun --watch src/cli.ts daemon`. **`--watch`, а НЕ `--hot`:** `--hot` перевыполняет entry, НЕ
  снося старые `Bun.sleep`-петли (`ensure` + `chatDelivery`) → они множатся на каждый reload (тот же
  класс лика, что грабля `bun --hot` в `engineering-conventions`). `--watch` рвёт старый event-loop
  и запускает entry заново со свежим состоянием (проверено `Bun.sleep`-пробником: после правки старое
  поколение петли молчит, тикает только новое) — процесс живёт под тем же pid (внутренний ре-экзек),
  но таймеры чистые. Демон идемпотентен (всё состояние с диска каждый тик, ensure/mirror по курсору),
  так что рестарт на сейв безопасен: сессии в tmux переживают, зеркало/доставка продолжаются с курсора.
- **Boot-guard пропущен из исходника** (`!IS_DEV` в `cmdDaemon`): он защищает ПРОД-БАНДЛ (откат в
  `.bak` при крашлупе), из dev откатывать нечего, а серия `--watch`-рестартов иначе пухла бы в ложные
  `boot-loop`-ошибки в логе.
- Практичный цикл TUI: правка → `q` → перезапуск (мгновенный). Для fullscreen alt-screen
  восстанавливает терминал на выходе.

## Headless e2e — тест интерактива через tmux
Интерактивный TUI нельзя протестировать без терминала — но tmux-пейн ЕСТЬ настоящий pty.
`scripts/tui-smoke.sh` (`bun smoke`) запускает реальный TUI в одноразовой tmux-сессии,
шлёт клавиши (`send-keys`) и снимает кадры (`capture-pane`) после каждого нажатия:

```
tmux new-session -d -s X -x 150 -y 34 'bun run src/cli.ts'
tmux send-keys -t X Down      # навигация
tmux send-keys -t X f         # fullscreen
tmux capture-pane -t X -p     # прочитать что нарисовалось
```
Безопасные клавиши только (nav / f / PgDn / q) — `s`/`r`/`D` не шлём, чтобы не трогать живые
сессии. Этот флоу ловит визуальные баги (ширина колонок, перенос строк, мангелинг контекста)
без живого терминала — то, что иначе ловит пользователь.

### Что смоук НЕ ловит — нужен глаз пользователя
`capture-pane -p` отдаёт **текстовую сетку символов**, а не картинку. Агент (Claude) видит
СТРУКТУРУ (что в какой клетке, перенос, выравнивание в предполагаемой моноширине), но **НЕ**
оценивает следующее — это судит только пользователь на своём терминале:
- **Цвет** — `-p` срезает ANSI-цвета. cyan/серый, контраст, не сливается ли — не видно.
- **Шрифт и ширина глифов** — box-drawing (`╭ │ ┃`), брайль-спиннер, вес `┃` vs `│`, эмодзи,
  широкие символы выравниваются по ШРИФТУ пользователя; в капче может быть ровно, у юзера —
  разъехаться. *(Реально кусало: ползунок `▐` выглядел «надкусанным» — поймал только юзер.)*
- **Размер терминала** — агент берёт свой (напр. 150×30); у юзера другой → иной перенос/колонки.
- **Анимация / мерцание / плавность** — капча статична; дёрганье и мигание не видны.
- **Мышь** — ощущение драга и ховера. Сами события в смоук посылаются: SGR-отчёт — это байты во
  входе панели, `tmux send-keys -t <pane> -l $'\e[<65;10;10M'` — колесо вниз над списком,
  `$'\e[<0;20;12M\e[<0;20;12m'` — клик по карточке. Разбор отчёта один (`src/tui/mouse.ts`),
  жесты — в `useMouse` (`src/tui/hooks/useMouse.ts`).

Вывод: смоук — для структурных багов. Эстетику (цвет, шрифт-зависимый рендер, ощущение анимации,
драг) агент сужает ВСЛЕПУЮ по сетке+коду — финальное «красиво/ровно» подтверждает пользователь.
Не заявлять «выглядит красиво» как факт — писать «структурно ок, визуал на тебе».

## Производительность рендера и время жизни (горячий цикл / сироты)
> Реальный инцидент 2026-06-11: `stitchmux-dev -f`, оставленный открытым, сжёг **~84% ядра 14 часов**.
> Два корня, оба теперь закрыты — но это легко вернуть регрессией, поэтому держим инварианты.

**Инвариант 1 — Ink-дерево перерисовывается только когда нужно.** В Ink ЛЮБОЙ `setState`
перерисовывает всё дерево (Yoga-layout + ANSI-diff), а fullscreen-транскрипт дорог (markdown-парс
на каждую видимую строку, расчёт высот). Поэтому:
- **Спиннер тикает ТОЛЬКО при активной работе.** `useSpinner(active)` запускает интервал лишь когда
  `items.some(it => it.status.active)` (есть «working»-сессия), и на 200мс, не 120мс. Состояние
  `sleeping` имеет `active: false` и не запускает спиннер; `SessionCard` включает `sleeping` и
  `pinned` в ручной компаратор `React.memo`. Idle/sleeping-флот = статичный кадр, **ноль ререндеров**. *(Был безусловный `setInterval(…,120)` → 8.3 ререндера/сек
  вечно, даже когда всё простаивает — это и жгло ядро.)*
- **Attach с авто-пробуждением.** Общий хелпер `src/tmux/attach.ts` используют и `stitchmux attach <name>`,
  и вход по Enter из TUI (`src/tui/run.tsx`): для спящей сессии сначала вызывается `wakeSessionByName`
  с прогрессом и ожиданием готовности, затем `attachTmux`. Клавиша `i` (compose) в fullscreen
  отключена на спящей карточке с подсказкой разбудить её через Enter.
- **`ChatMessage` и `Markdown` мемоизированы** (`React.memo`). `ChatMessage` сравнивается по
  ИДЕНТИЧНОСТИ сообщения (`a.msg === b.msg`); спиннер-тик и fleet-поллинг (1.5с) перерисовывают App,
  но НЕ пересобирают массив сообщений → история не перерендерится и markdown не перепарсится. `spin`
  сравнивается только для `tool_call`-строк (анимированный глиф). `Markdown` мемоизирован как
  чистый parse-leaf.
- **`useTranscript` гейтит ре-парс по mtime** — перечитывает jsonl только когда файл изменился
  (idle-сессия = ноль работы вместо ре-парса 300 сообщений каждые 1.5с).

**Инвариант 2 — TUI умирает вместе с терминалом, не сиротеет.** Закрытие вкладки VS Code/iTerm
переусыновляет процесс к PID 1; без явного выхода render-loop (живой за счёт интервалов) рендерит в
мёртвый pty вечно. На дефолт сигналов полагаться НЕЛЬЗЯ — Ink/Bun их глушат (сирота игнорировал даже
`kill`/SIGTERM). `installExitOnTerminalDeath()` (`src/tui/run.tsx`) форсит `process.exit(0)` на
`SIGHUP`/`SIGTERM`, на первой же ошибке записи в stdout (EIO на мёртвом pty) и на EOF stdin.

**Выход нельзя остановить.** Закрываемая вкладка может вернуть передний план оболочке раньше, чем
до TUI дойдёт `SIGHUP`. Из фоновой группы любое переключение режима терминала (`tcsetattr`; его
делает и наш `setRawMode(false)`, и exit-хук Ink через `signal-exit` → unmount) ядро останавливает
сигналом `SIGTTOU`. Защёлка `dying` глотает следующие сигналы, и процесс навсегда стоит в состоянии
`T` без владельца: CPU не ест, поэтому его видно только по проверке владельца. Поэтому `die()` первым
делом ставит `SIGTTOU`/`SIGTTIN` в игнор через `signal(2)` из libc (`src/tui/terminalStops.ts`):
при игноре вызов просто проходит. JS-обработчик не годится: Bun ставит его с `SA_RESTART`, и
прерванный `tcsetattr` перезапускается по кругу. При смерти терминала (`SIGHUP`, ошибки и EOF
stdin/stdout) терминал сами не восстанавливаем, восстанавливаем только на `SIGTERM`. Несущий тест —
`test/tui-terminal-death.test.ts`: настоящий pty, TUI уведён в фон, сигнал, выход за секунду; контроль
— программа без защиты обязана встать на `SIGTTOU`.

### Как дебажить «комп горячий» / подозрение на горячий TUI
1. **Найти жор:** `ps aux | grep -E "src/cli.ts|stitchmux.js" | grep -v grep` — смотри `%CPU` и колонку
   времени. `bun run src/cli.ts` на ~целом ядре часами = горячий цикл рендера.
2. **Сирота?** `ps -o pid,ppid,tty,stat -p <PID>` — `PPID=1` + `STAT` с `+` на мёртвом tty = процесс
   осиротел (терминал закрыт, а он жив). `STAT` `T` = остановлен job-control сигналом на выходе
   (на Linux `cat /proc/<PID>/syscall`: первое число `16` — `ioctl`, третье `0x5403` — `TCSETSW`).
   Это всегда баг — терминал должен был его убить.
3. **Убить:** обычный `kill` сирота может проглотить (сигналы перехвачены) → `kill -9 <PID>`. Это
   безопасно: сессиями рулит ДЕМОН (отдельный процесс, не Ink) — TUI лишь интерактивное меню.
4. **Замер инварианта:** запусти TUI в одноразовом tmux-пейне (`tmux new-session -d -s t 'bun run
   src/cli.ts -f'`), сэмпли `ps -o %cpu= -p <PID>` — на простаивающем флоте должно быть ~0%. Не ноль
   → проверь, не тикает ли спиннер без активных сессий (Инвариант 1).
5. **Проверка exit-on-death:** подними TUI в tmux-пейне, `tmux kill-session -t t`, через секунду
   `ps -p <PID>` — процесс ОБЯЗАН исчезнуть; в `~/.stitchmux/stitchmux.log` будет `terminal died — exiting`.

**Демон НЕ затронут** ничем из этого — он не крутит Ink. Горит/сиротеет только интерактивное меню.

## Порядок списка и выбор (activity-sort, identity-курсор)
Список (fullscreen и inline) отсортирован **по последней активности беседы** (mtime jsonl,
`row.lastActivityMs`), новые сверху; managed и external сортируются каждый внутри своей секции
(`fleet.buildItems`). На карточке активность видна как `· 5m ago` (`activityText`,
предвычисляется в `buildItems`); аптайм tmux показывается отдельно как `up 2d` и только у
запущенных (`uptimeSeconds !== null`).

Живая сортировка однажды уже выпиливалась («карточки прыгают на каждом тике — навигация
неюзабельна»). Корень закрыт двумя стабилизаторами + одним инвариантом выбора:
- **Ключ сортировки огрублён до минуты** (`activityBucket`) — активно пишущие сессии меняются
  местами максимум раз в минуту, не на каждый полл; внутри бакета — детерминированный порядок
  по имени.
- **Нет транскрипта** (свежесозданная сессия) → фолбэк на время старта tmux (`createdAt`),
  совсем ничего → низ списка.
- **Курсор привязан к uuid сессии, не к индексу** (`selKey` в `App.tsx`): пересортировка
  двигает карточки, но выделенной остаётся ТА ЖЕ сессия, и окно скролла доезжает за ней
  (`revealCursor` на смену `cur`). Удалили выделенную — фолбэк на ту же позицию списка.

Регрессии ловит `test/fleet.test.ts` (порядок, бакет-стабильность, фолбэки, activityText).
CLI `stitchmux list` осознанно НЕ сортируется — там порядок реестра (детерминизм для скриптов).

## Окно списка: рисуется только то, что влезает
**Кадр выше терминала — это кадр, который терминал ПРОКРУЧИВАЕТ сам.** Ink переписывает свой кадр
на месте, пока тот помещается в экран; как только не помещается, каждая перерисовка (нажатие,
полл раз в 1.5 с) оказывается в конце буфера — человек, отлиставший наверх, возвращается вниз, а
его стрелка выглядит как прыжок. Поэтому оба вида рисуют ТОЛЬКО окно: `src/tui/listWindow.ts`
считает геометрию, `App.tsx` держит `listScroll` и доводит курсор (`revealCursor`), а вид получает
`winStart`/`visibleCards` и режет список срезом.

- **Fullscreen** — фиксированный шаг карточки (`CARD_H`), окно = высота панели / шаг.
- **Inline** — карточки разной высоты (managed 3 строки с зазором, external 4) плюс строка
  разделителя перед секцией external, поэтому окно считается сложением высот (`inlineFit`,
  `inlineMaxStart`, `inlineReveal`), а не делением. В шапке видно, какой это срез: `4–9/17`.
- **Высота external-карточки фиксирована тем, что её две строки доказательств ОБРЕЗАЮТСЯ**
  (`externalInlineLines`): перенос строки ломает бюджет окна и возвращает прокрутку.
- Окно пересчитывается на ресайз терминала, и курсор доводится туда же — иначе после сжатия
  окна выделенная карточка остаётся за кадром.

Размеры берутся из `useWindowSize()` Ink 8: высота для бюджета списка и ширина для
обрезки строк и границ панелей. Mouse handler читает актуальную ширину через ref;
resize не снимает обработчики посреди drag и не теряет текущую геометрию.

Регрессии ловит `test/tui-list-window.test.ts`, включая свойство «после любого доскролла сумма
высот окна не больше высоты терминала» на 17, 200 и 500 сессиях.

## Знак вендора рядом с моделью
Колонка рантайма говорит, какой харнесс держит сессию (`claude` / `codex` / `opencode`), и НЕ
говорит, чья модель отвечает: у OpenCode и Custom-рецептов это разные вещи. Знак вендора
(`src/inventory/vendor.ts`) — одна ячейка в фирменном цвете перед моделью: Anthropic `✳` `#D97757`,
OpenAI `✻` белый, DeepSeek `≋` `#4D6BFE`, Google `✦` `#4285F4`. Он виден везде, где показана
модель: строка и карточка TUI, `stitchmux list`, `stitchmux fleet`, минимальная строка статуса.

- **Определение — преобразование, а не каталог**: id вида `vendor/model` отвечает своим префиксом,
  остальные — по семейству (`claude-*`, `opus`, `gpt-*`, `o3`, `deepseek*`, `gemini*`). Новая
  семья вендора резолвится без правки кода.
- **Строка несёт `modelId` рядом с `model`**: витринная подпись уже потеряла префикс вендора
  (`claude-mythos-6` → `Mythos 6`), и по ней ответить, кто автор, нельзя — по сырому id можно.
  Пир, который поля ещё не присылает, просто остаётся без знака.
- **Чего не знаем — не помечаем**, но ячейку всё равно резервируем: иначе колонка моделей
  разъезжается между строками со знаком и без. Эмодзи не годятся: две ячейки.

## Модель IO/поллинга (mtime-кэш + видимый захват)
Если рендер-цикл холодный (раздел выше), второй источник нагрузки — **IO-слой поллинга**: каждые
1.5с (`useFleet`) и 4с (`useDiscover`) перечитывались и перепарсивались транскрипты, даже если
файлы не менялись, плюс форк `tmux capture-pane` на КАЖДУЮ запущенную сессию. Инварианты, чтобы
idle-флот делал почти ничего:

- **Один источник кэша — `src/util/mtimeCache.ts` (`MtimeCache`).** Кэширует по `(path, mtime)` и
  возвращает **ту же ссылку**, пока файл не менялся. Это даёт ДВА эффекта сразу: (1) нет повторного
  чтения/парса; (2) downstream `React.memo` (`SessionCard`, `ChatMessage`) видит стабильный
  `lastMessage` и бейлит. Ломается одно — ломается и memo. Консьюмеры: `lastTranscriptMessage`,
  `sessionUsedTokens` (`agent/index.ts`), `discoverActive` (`tui/discover.ts`).
- **Никаких полных чтений транскрипта.** Большие jsonl читаются хвостом (`readTailLines`, чанки с
  конца) + при нужде головой (`readHead`, 64КБ — только для cwd). `discover` больше НЕ делает
  `readFileSync` целиком (было доминирующей IO-стоимостью на мегабайтных файлах).
- **Захват пейна — только для видимых карточек.** `collectRows(m, { liveNames })`: TUI передаёт имена
  видимых (окно скролла) + выбранной сессии; их пейны форкаются (`capture-pane`), остальные запущенные
  переиспользуют последний скан из `scanCache` (`inventory/rows.ts`). Оффскрин-состояние невидимо и
  освежается при скролле карточки в окно. **CLI `list` зовёт `collectRows` БЕЗ `liveNames` → захват
  всех** (корректность таблицы). Форки масштабируются по экрану, не по размеру флота (важно для 20+).
- **Высоты сообщений кэшируются** (`chatMessageHeight`, WeakMap по `msg`×`width`) — `sanitize`+`wrap`
  не гоняются в measure-циклах транскрипта на каждый ререндер.

### Дебаг IO-нагрузки
- Idle-флот должен давать **ноль** дисковых чтений транскриптов между записями — если `discover`/`list`
  читают мегабайты, проверь, что путь идёт через `MtimeCache` (не зови `readFileSync` на jsonl напрямую).
- Карточки не должны перерисовываться на поллинг, если контент тот же — сломанный memo обычно значит,
  что `lastMessage` потерял стабильную ссылку (консьюмер обошёл `MtimeCache`) или компаратор
  `SessionCard` не покрыл новое рендер-поле.
- Лишние `tmux`-форки — проверь, что `liveNames` доходит до `collectRows` (через `liveNamesRef` в
  `App.tsx` → `useFleet`); пустой/отсутствующий → захват всех.
