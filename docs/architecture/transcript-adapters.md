# Транскрипт-адаптеры

`stats.usage` читает [канонический usage ledger](usage.md), как CLI/control и расход субагентов.
Usage display-блоков не суммируется: native message identity и cumulative semantics обрабатывает
один reducer. Index/checkpoint и usage contributions публикуются атомарно в SQLite cache.

ccmux агент-агностичен: сессию может бэкать разный агентский CLI. Их форматы истории
**структурно разные**, поэтому чтение идёт через **адаптер на формат + единый контракт**
`TranscriptMessage` (Zod, `agent/transcript/messageSchema.ts`). Никакого union-парсера с if-ветками.

## Контракт

`TranscriptMessage`: `{ id, seq, createdAt, role, kind, text, title, toolName, toolCallId, status, rawType }`.
- `role`: user · assistant · tool · system · unknown
- `kind`: message · tool_call · tool_result · thinking · event · unknown

Это же сообщение переиспользуется как `lastMessage` в `list --json` («где остановилось»).

### Картинки в Claude JSONL

Поле `image` описывает самостоятельную картинку; optional `resultImages` описывает картинки
результата инструмента на той же `TranscriptImageSchema` (`address`, `mediaType`, `bytes`,
`digest`, `unavailable`). Без таких картинок ключ отсутствует. Байты в сообщения не включаются;
`resultText` сохраняет текстовые маркеры `[image]`.

Адаптер собирает дескрипторы из исходного `tool_result.content` до clipping текста и связывает
их с `tool_call` по `tool_use_id`. Если вызов за границей окна, дескрипторы остаются на
самостоятельном `tool_result`. Картинки не добавляют пользовательских сообщений и не меняют
счётчики usage/stats. Control transcript и CLI JSON используют тот же контракт.

`ccmux transcript <target> --image <address>` выдаёт одну картинку как data URL. Адрес обычной
картинки — `<entry-uuid>#<outer>`; адрес картинки результата — `<entry-uuid>#<outer>/<inner>`.
Оба индекса — позиции исходных блоков, включая текст: `outer` в `message.content`, `inner`
в `tool_result.content`. Адрес не зависит от пагинации или лимита текста; потребитель передаёт
его обратно целиком. Путь к локальному файлу или внешний URL в адресе не допускается.

`src/agent/claude/images.ts` владеет адресацией, описанием и чтением. Источник base64 ограничен
8 MiB декодированных байт; размер учитывает padding, digest — SHA-256 encoded content.
Неизвестный источник — `unsupported-source`, повреждённые данные/адрес или отсутствующая
запись — `malformed`, превышение лимита — `too-large`. URL-source не скачивается.
Descriptor и reader применяют одинаковые проверки. Выдача CLI ждёт завершения записи в stdout,
чтобы pipe получил целый data URL. Offset/stats index не хранит сообщения; добавление
дескрипторов не требует смены parser revision или массовой перестройки индексов.

## Интерфейс provider (`src/agent/index.ts`)

```ts
interface AgentProvider {
  id: "claude" | "codex";
  buildArgv(...): string[];
  launchEnv(...): Record<string, string>;
  historyFile(session, m): string | null;
  parse(lines, startLine, textLimit?): TranscriptMessage[];
  usedTokens(lines): number | null;
  lastModel(lines): string | null;
  scanPane(paneText): PaneScan;
}
```
Выбор provider — по `Session.agent` (`getProvider`/`providerFor`). IO + tail/cursor-окно живут в
`src/agent/transcript/transcriptRead.ts` (`readTranscriptFile`); managed lookup и previews остаются в
`src/agent/index.ts` (`readTranscript` / `lastTranscriptMessage` / `sessionUsedTokens`). Format
adapters остаются чистыми трансформами. `detect(lines)` — сниффер формата по содержимому для
неизвестного исторического файла.

Окно строк у всех адаптеров обходит `transcriptEntries` (`src/agent/transcript/lines.ts`):
абсолютный номер строки — курсор (`transcript --cursor` возвращает его же), пустые, недописанные
и не-объектные строки пропускаются. Адаптер решает только, что значит запись.

Раскладка `src/agent/`: `<provider>/` — адаптеры провайдеров; `transcript/` — чтение, индекс,
сниффер формата, нормализация и сводки инструментов; `launch/` — входы запуска, stamp, окружение
сессии (`providerLaunchEnv`) и ssh-агент; `prompt/` — managed prompt и его модули; `index.ts` —
реестр провайдеров; у Codex процесс-владелец App Server — отдельная папка `codex/owned/`.
Файлы статуса сессии живут в `src/session/` (`status.ts`, `metricsFile.ts`), подпись модели — в
`src/inventory/` (`modelName.ts`, `vendor.ts`).

## Exact external selection

`ccmux transcript 'external:<provider>:<machine>#<UUID>' --json` принимает точный key
из inventory для Codex и Claude. Встроенная machine выбирает existing fleet transport,
provider выбирает штатный parser. Это storage selector, не managed session alias и не
новый write address. Remote hop сохраняет key целиком; cwd/path не принимаются от caller.

`ccmux transcript app/<UUID> --json --tail 3` и форма с префиксом машины
`<machine>:app/<UUID>` читают persisted Codex JSONL без adopt, fork, запуска provider или записи
managed registry. Имя задачи и cwd не участвуют в lookup. Как и явный CLI `external`, чтение
не требует включения автоматического fleet scanning через `externalInventory`. Доступ задаётся
host account и разрешённым remote CLI transport; managed UUID требует managed address.
Service API `external.history` сохраняет собственный access policy и не расширяется этой командой.

`src/external/storage.ts` владеет общим с external-content lookup: configured root,
не более 8192 entries и восьми уровней, exact UUID filename и совпадающая metadata identity.
Codex проверяет первую `session_meta`; Claude — bounded metadata с `sessionId`.
Claude registry UUID и native continuation ID исключены из external read одинаково.
Требуются same-user regular file и отсутствие group/world write; symlink не обходится.
`src/external/transcript.ts` подключает подтверждённый файл к общему line reader.

Tail и backward limit ограничены 1000 строками. `seq` и `--cursor` — абсолютные номера
завершённых JSONL-строк; `--before LINE --limit N` читает предыдущее окно. Незавершённая последняя
строка появится только после newline. Первый запрос индексирует файл потоково, последующие
индексируют append; forward cursor сохраняет существующее значение «всё после LINE».

Индекс строк выбирается по явному provider и лежит в `<cache>/ccmux/transcript-index/`: revision 1
— `<sha256(path)>.sqlite`, revision n — `<sha256(path)>-v<n>.sqlite`. Claude и Codex на revision 2:
парсер Claude не считает сообщениями копии запросов к модели (`api-request-blob`), парсер Codex
читает custom tool calls. Счётчики `stats` — нарастающий итог по файлу, поэтому уже посчитанное
исправляет только пересборка: смена revision даёт индексу новое имя, и файл читается целиком один
раз при первом обращении; usage-факты строятся заново в том же новом хранилище, старое никто не
читает. Namespace и сохранённая revision
меняются только при изменении семантики соответствующего парсера; metadata проверяет revision
вместе с provider. Готовые offsets/statistics неизменившегося парсера переиспользуются без
повторного чтения истории. Путь транскрипта записан в метаданных (`source`). Демон раз в сутки (первый раз — через минуту после старта)
убирает кэш (`pruneTranscriptIndexes`): индекс, чей записанный транскрипт исчез; индекс, построенный
ушедшей parser revision; индекс, который 14 дней никто не продвигал; файлы прежнего JSON-формата. Индекс открывается ради `source` только
после суток покоя: закрытие последнего соединения с базой в WAL-режиме может снять её журнал из-под
пишущего. Проход уступает цикл каждые 100 индексов. Удалённый индекс, чей транскрипт ещё читают,
перестраивается при следующем чтении — это цена прохода по файлу, не потеря данных.
`--last-message` возвращает последний assistant text из bounded окна; external `--image`
явно не поддерживается. Это полный transcript projection, не authored-text external.history API
с его отдельным revision-pinned byte cursor.

Роль `user` означает native роль записи, а не криптографическое доказательство, что
текст напечатал человек: caller проверяет происхождение разрешения отдельно. Отсутствующая
native отметка времени остаётся null; время чтения не подставляется вместо неё.

Stored transcript: `source.available=true`, `kind=codex-jsonl|claude-jsonl`, exit 0; пустое успешно прочитанное
окно остаётся доступным. Missing: `source.available=false`, error `transcript file not found`.
Unreadable, invalid metadata, ambiguous identity или смена файла: false и `transcript file unreadable`.
В обоих отказах JSON содержит пустые messages и null cursor, exit 1; неизвестные cwd/path — пустые
строки. Неверный UUID и managed identity дают явный CLI refusal. Для external `session.rc`
содержит переданный inventory key либо exact `<machine>:app/<UUID>`; managed RC labels не меняются.
Неподдержанный provider возвращает `external transcript provider is unsupported`, exit 1.

## Custom tools Codex

Codex adapter сохраняет `custom_tool_call` с текстовым `input` и объединяет
`custom_tool_call_output` по native `call_id`, как обычные function calls. Structured output
преобразуется в текстовые блоки; нетекстовые части получают явные маркеры. Native error
остаётся ошибкой, а вызов без результата остаётся незавершённым. При чтении разных окон
результат связывается через общий fold, без выдуманной завершённости.

`text-limit` ограничивает каждую возвращаемую текстовую запись. Полнота последовательности
не обещает неограниченный текст, скрытое reasoning или бинарные image payloads. Derived index
имеет schema version 2 и отдельное имя файла: reader другой версии не получает несовместимый
cache. Невалидный или прежний индекс перестраивается из неизменённого provider transcript.
`test/codex-custom-transcript.test.ts` проверяет calls, ошибки, результаты в разных окнах,
malformed записи и пересборку индекса.

## Нативные рантаймы без файла транскрипта

Часть нативных рантаймов не пишет jsonl: openCode и custom хранят переписку в собственной
структурированной истории. Для них `ccmux transcript` и control `transcript.read` отвечают из
того же feed, что и `history.read`, а не ищут несуществующий файл. Признак ветки — источник, а не
режим: `providerFor(session).historyFile(session, m) === null`. Это НЕ `hasNativeRuntime`:
codex app-server нативен, но его rollout-файл настоящий, и уводить его на feed значило бы
обменять рабочий транскрипт на частичный.

Окно собирает `src/context/transcriptWindow.ts`. Рантайм листает историю назад (первая страница —
самые новые записи, курсор ведёт к более старым), поэтому читатель забирает страницы до
`completeness: complete` и разворачивает их порядок: получается вся переписка по возрастанию.
Над ней применяется та же арифметика `tail`/`cursor`/`before`/`limit`, что и над строками файла,
и `seq` — абсолютный номер записи, так что курсор потребителя сохраняет смысл. `mtimeMs` равен
`null` (у feed нет времени файла), `source.kind` — `<agent>-native`.
`src/context/nativeTranscriptHistory.ts` принимает только полную цепочку: без пропущенных
entries, повторных item IDs/cursors, смены native identity/revision и противоречивых границ.
Без начала беседы абсолютная нумерация невозможна: неполный суффикс не получает seq/cursor.
Чтение ограничено общим deadline 5 секунд, 65 536 entries и 32 MiB сериализованных entries.
Превышение бюджета, `unknown` или неполная цепочка дают `source.available=false`, не успешное
пустое окно. Внешняя отмена действует и при ожидании mailbox-lock. При большой истории,
не помещающейся в эти бюджеты, для постраничного чтения предназначен `history.read`.

OpenCode native pagination (`src/context/opencodeHistory.ts`) ограничивает число **parts**, а
не только сообщений. Страница возвращает новейшие parts; cursor сохраняет opaque upstream
cursor и пары native message/part IDs для оставшегося префикса. Продолжение читает эти ID через
тот же authenticated SDK, не перечитывает изменившуюся голову списка и не хранит копии текста.
Чтение оставшегося суффикса имеет concurrency не выше восьми. Удалённый anchor отвергается;
generation/revision проверяет общий history cursor. Текстовые и image-бюджеты feed сохраняются:
полнота последовательности entries не означает неограниченный объём текста каждой записи.

Claude в нативном режиме остаётся файловым: рантайм пишет собственный jsonl рядом со своими
`projects`, и его читает тот же claude-парсер по `nativeTranscriptPath`, с абсолютными строками.
Он не проходит через feed. Неподдержанный `--agent` (субагент) для не-Claude нативного рантайма
даёт `unavailable` со словами «this runtime keeps no agent transcripts»; у Claude нативного
субагентский файл лежит рядом с основным и читается тем же путём.

Отсутствие живого владельца — это «не знаю», а не «пусто»: если feed недоступен, ответ
`available: false` с названной причиной, а не пустая успешная лента.

## Поиск по истории (`transcript --grep`)

`ccmux transcript <addr> --grep PATTERN` ищет по **всей** истории сессии тем же адресом, что и
остальные чтения: managed, `machine:session`, App thread и `external:…`. Реализация —
`src/context/transcriptSearch.ts` (поиск) и `src/commands/transcriptSearch.ts` (CLI, вывод).

Поиск не открывает хранилище сам: он читает через тот же window reader, что `--json`, окнами
`--before/--limit`. Поэтому file-backed, нативный и внешний рантаймы дают один и тот же ответ о
содержимом, а `seq` совпадения — это абсолютная строка, которую принимают `--before` и `--cursor`.

- **Что ищется.** Текст сообщения (`text`), аргументы инструмента (`input`) и его сложенный
  результат (`output`). Аргументы раскодируются из JSON: строковые значения ищутся как написаны,
  без `\n` и удвоенных `\`. id, uuid, пути, timestamp и прочая служебная часть записи не
  ищутся.
- **Диапазон.** По умолчанию — вся история. `--cursor`, `--before`, явный `--tail` сужают его.
  Ответ всегда называет просмотренный диапазон и число сообщений, включая явный ноль: «не нашёл»
  нельзя спутать с «не смотрел».
- **Совпадения.** По умолчанию до 50, `--limit` до 1000; оставляются **новейшие**, итог считает
  все и говорит, как дойти до более старых (`--before <SEQ самого старого показанного>`).
- **Шаблон.** Регулярное выражение JavaScript; `-F` — литерал. Регистр smart-case: без заглавной
  буквы — без учёта регистра (escape вроде `\S` заглавной не считается); `-i`/`-s` задают явно.
  Пустой, некорректный или совпадающий с пустой строкой шаблон отклоняется до чтения.
- **Фильтры.** `--role` и `--kind` принимают значения контракта через запятую; неизвестное
  значение отклоняется со списком допустимых.
- **Вывод.** Таблица `SEQ AGE ROLE KIND FIELD MATCH` с выдержкой вокруг первого совпадения
  (`(+N)` — ещё совпадения в том же сообщении); на TTY совпадение подсвечено. `--json` — та же
  шапка `session/source`, что у окна, плюс `query`, `scanned`, `total`, `truncated`, `matches`
  с `excerpt: {before, match, after}`. Exit 0 — найдено, 1 — не найдено или не прочитано
  (строка говорит, что именно).

Файл читается пачками по ~32 МБ исходных байт (250–4000 строк), со сборкой мусора между ними:
размер строки у Claude (~2 КБ) и Codex (~26 КБ) отличается на порядок, и число строк как единица
давало либо медленный поиск, либо пик в 1,6 ГБ. Замер на всей истории: 94 МБ Claude — 0,4 с и
217 МБ пика; 774 МБ Codex — 0,9 с и 571 МБ. Результат инструмента, попавший в следующую пачку
после своего вызова, не складывается в вызов, а находится как отдельный `tool_result` на своей
строке — текст и номер строки при этом верны. Нативный рантайм без индекса строк читается одним
окном.

## Поиск по всем разговорам (`search`)

`ccmux search` отвечает на вопрос, в котором ещё нет сессии: где это обсуждали, как это чинили,
что вчера решили. Он читает **хранилище**, а не список сессий, поэтому видит разговоры, чья сессия
удалена, заменена форком или никогда не была managed. Реализация — `src/context/storedConversations.ts`
(перечень), `src/context/corpusSearch.ts` (чтение и совпадения), `src/context/corpusShards.ts`
(раскладка по процессам), `src/commands/search.ts` (CLI, флот, вывод); wire-форма —
`src/context/corpusSearchSchema.ts`.

**Перечень разговоров машины.** Claude: каждый `<uuid>.jsonl` во всех известных profile roots
(`knownProjectsDirs`). Codex: каждый `rollout-*.jsonl[.zst]` в `sessions` и соседнем
`archived_sessions`, сгруппированные по треду. Транскрипты порождённых агентов (файлы рядом с
сессией Claude) разговорами не считаются: это работа инструмента, она читается через `--agent`
родителя.

**Адрес.** Тот, который принимает `ccmux transcript`: `<машина>:<имя>` для файла, который managed-
сессия читает сейчас, и `external:<provider>:<машина>#<uuid>` для всего остального. Поле `lines`
говорит, открывает ли адрес найденную строку: ранний или сжатый файл Codex и второй файл Claude
под id, которым владеет сессия, ищутся, но построчно не читаются — в выводе `SEQ` у них `-`.
Внешний читатель ищет id Claude во всех известных profile roots, начиная с корня машины.

**Три вопроса одной командой.**

- `search PATTERN` — строки: совпадения, сгруппированные под адресом разговора, с `SEQ`, возрастом,
  ролью и выдержкой. Остаются новейшие `--limit` (50), итог считает все.
- `search PATTERN --map` — где жила тема: строка на разговор со счётчиками (все, пользователя,
  агента), первым днём, возрастом последнего совпадения и новейшей строкой. Считаются все
  совпадения, а не только поместившиеся в `--limit`: тема, о которой говорили месяцами, даёт тысячи
  строк, и новейшие пятьдесят все из этой недели.
- `search --project X` или `search --since WHEN` без шаблона — конспект: каждое сообщение
  пользователя и последний ответ агента на него, по порядку. Промежуточные реплики агента между
  вызовами инструментов в конспект не входят.

**Что считается сказанным.** По умолчанию ищется вид `message` у ролей `user` и `assistant`:
по объёму разговор — это вывод инструментов, и найденная там фраза редко тот разговор, который
ищут. Текст, который harness вставил на сторону пользователя (reminder, вывод hook, уведомление о
фоновой задаче, сводка после сжатия контекста, `environment_context` и инструкции Codex), поиск
относит к роли `system`: это говорит harness, а не человек. `--kind` и `--role` выбирают иначе;
названный `--kind` снимает предположение о роли, потому что роль результата инструмента — `tool`.

**Фильтры.** `--project` — часть рабочего каталога, имени сессии или проекта, который объявляет
репозиторий каталога, без учёта регистра;
`--since`/`--until` — `today`, `yesterday`, `7d`/`12h`/`2w`, день или timestamp (день — весь день
в поясе машины); `--provider`; `--machine`/`--local`. Файл, в котором по времени последней записи
не может быть сообщения из диапазона, и файл Codex, начатый позже конца диапазона, не читаются и
считаются в `skippedFiles`. Сообщение без времени ни в один диапазон дат не входит.

**Чтение.** Каждый файл читается потоком один раз, тем же парсером провайдера и тем же
`matchMessage`, что у `transcript --grep`; строки нумеруются так же, как в индексе транскрипта,
поэтому `SEQ` принимает `--before`. Индекса и фоновой работы между поисками нет. Парсеру не
передаётся путь источника: с ним он открывает транскрипт каждого порождённого агента ради описания
вызова, и это одно увеличивало чтение 5,8 ГБ с 10 до 46 с. Строки режутся по байту перевода строки:
строка Codex доходит до 26 МБ и приходит кусками, склейка её как текста стоила квадрата длины
(150 с на 2 ГБ при 7 с распаковки).

**Процессы.** Чтение разговора — это декодирование и JSON-разбор на одном ядре. Разговоры
независимы, поэтому раздаются по размеру нескольким копиям программы (`_search-shard`, до 6, одна
на 512 МБ, одно ядро остаётся машине); каждая возвращает свои новейшие совпадения. Доля, чей
процесс не ответил, читается в основном процессе — непрочитанной она не остаётся. Замер на 14,8 ГБ
(269 разговоров, 271 файл): один процесс — 41–74 с в зависимости от загрузки машины, шесть —
10–13 с; поиск за сутки по одному проекту — меньше секунды.

**Чей разговор и весь текст.** Каждое совпадение и каждый разговор в `--json` несут `repository`
(`owner/name` из `origin` рабочего каталога, пока каталог остаётся checkout), `project` — проект,
который этот репозиторий называет своим в `.passport.json` (поля нет, если объявления нет), и
`ofSession` — сессию,
которой разговор принадлежит или принадлежал: читающую его сейчас либо ту, под чьим заголовком
открывается файл, оставленный ею при `/clear`, форке или сжатии. Правила принадлежности — в
[идентичности сессии](session-identity.md). `--full` кладёт в `text` весь текст сообщения вместо
выдержки; без него `text` равен `null`. Вывод для человека `--full` не принимает: строка на
совпадение целое сообщение не вмещает. `search --schema` печатает JSON Schema ответа.

**Квитанции по метке.** `search PATTERN --receipts` отвечает, куда попало каждое разное значение,
найденное шаблоном: ключ совпадения возвращает тот же сопоставитель, что ищет строки, сбор идёт в
том же проходе, доли и машины сливаются одной функцией (`mergeReceipts`). Форма и правила — в
[идентичности сессии](session-identity.md#куда-попало-сообщение-с-меткой). В шаблоне `^` и `$` —
края строки сообщения, а не всего сообщения: сообщение многострочно, и поиск ведёт себя как
построчный — и здесь, и в `transcript --grep`.

**Флот.** Каждая машина ищет в своём хранилище: команда выполняет поиск здесь и просит остальные
машины выполнить его же с `--local --json`, передавая скомпилированный шаблон и абсолютные времена.
Разговоры между машинами не ходят, только совпадения. Машина, которая не ответила или не знает
команду, названа строкой `NOT SEARCHED` с причиной; её молчание — не «совпадений нет». Exit 0 —
найдено, 1 — не найдено, 2 — не найдено, и при этом какая-то машина не была просмотрена.

## Файлы одного треда Codex

Codex держит один тред в нескольких файлах, когда он длинный: Desktop делит его на
`rollout-<time>-<id>.jsonl` и последующие `rollout-<time>-<id>_<segment>.jsonl`, а законченные или
давно не тронутые файлы сжимает в `.jsonl.zst` (CLI делает это и с целыми простаивающими тредами).
В каждом файле первая запись — `session_meta` треда. Разбор имён один:
`src/agent/codex/rolloutFiles.ts` (`parseRolloutName`, `codexRolloutFiles`, `currentRolloutFile`).

- `historyFile` Codex — текущий файл: самый новый несжатый. Его читают transcript, статус и расход.
  Более ранние файлы в окно не входят; transcript JSON сообщает их число в `window.earlierFiles`,
  и `reachedStart` относится только к прочитанному файлу.
- Есть ли беседа, решает `codexHistoryPresent`: любой файл треда, в том числе сжатый. Супервизор
  (`src/commands/run.ts`) и native-запуск больше не блокируют сессию как «missing rollout», если
  Codex сжал её журнал; resume сжатого треда делает сам Codex.
- Обнаружение внешних тредов показывает тред один раз, по текущему файлу.

## Форматы (выверено на реальных файлах)

| | Claude Code | Codex |
|---|---|---|
| Файл | `~/.claude/projects/<enc-cwd>/<uuid>.jsonl` | `~/.codex/sessions/Y/M/D/rollout-*-<id>.jsonl`; длинный тред — ещё `rollout-*-<id>_<segment>.jsonl`, готовые файлы бывают `.jsonl.zst` |
| Обёртка | `.type` = роль; `.message.content[]` | `.type=response_item`; `.payload` |
| text | `{type:text\|thinking, …}` | `{type:input_text\|output_text}` |
| tool call | inline `{type:tool_use, name, id, input}` | top-level `{function_call, name, arguments(JSON-строка), call_id}` |
| tool result | user `{type:tool_result, tool_use_id, content}` | `{function_call_output, call_id, output}` |
| reasoning | `{type:thinking, thinking}` (текст есть) | `{reasoning, encrypted_content, summary[]}` → текст сводки, при `summary: []` — `text: null` |
| токены | `.message.usage` | отдельный `event_msg/token_count → info.*_token_usage` |
| роли | user/assistant | user/assistant/**developer**(→system) |

У Claude две записи читаются не как обёртка «роль + `message`». `type: attachment` с
`attachment.type: queued_command` — то, что поставлено в очередь, пока шёл ход: сообщение человека
(`humanTurn: true`) или слово самого рантайма (уведомление о завершении фоновой задачи); текст или
блоки лежат в `attachment.prompt`, время — в `timestamp`, и читается это как сообщение пользователя.
`type: api-request-blob` — копия отправленного модели по хэшу, без времени: всё, что в ней есть, уже
записано своими датированными записями, поэтому сообщением разговора она не считается.

Отсутствие сводки — признак в данных, а не строка. У зашифрованного размышления `text` равен `null`
при `rawType: 'reasoning'`; заглушки в тексте нет. Строка-заглушка заставляла бы потребителя узнавать
её сверкой по тексту, и эта сверка неверна в обе стороны: настоящая сводка, случайно так
написанная, была бы проглочена, а смена формулировки у нас молча превратила бы все заглушки в
содержимое. Поток содержимого control-service тем же правилом живёт с самого начала — он публикует
`reasoning-summary` только когда сводка есть.

## Субагенты Claude и время конца вызова

Claude Code запускает субагентов инструментом `Agent`. В файле сессии это выглядит так: `tool_use`
с `subagent_type`/`description`/`prompt`, через доли секунды `tool_result` «Async agent launched
successfully» — а на самой записи результата, в `toolUseResult`, лежит `agentId`, `status:
async_launched`, `resolvedModel`. Субагент пишет свой транскрипт в
`<uuid>/subagents/agent-<id>.jsonl` рядом с файлом сессии (плюс `agent-<id>.meta.json`), а закончив,
рантайм вставляет в основную ленту `user`-сообщение `<task-notification>` с `<tool-use-id>`,
`<status>` и `<result>` — итоговым текстом субагента.

Адаптер (`src/agent/claude/transcript.ts`, `src/agent/claude/subagent.ts`) делает из этого одну
запись:

- у вызова `Agent` есть `agent`: id, тип, описание, модель, `state` (`running` | `finished`),
  начало и конец, число вызовов инструментов и суммарный расход из файла субагента, `available`
  (файл был на месте). Расход считается по одному разу на API-сообщение: блоки одного ответа делят
  `message.id`, и без этого двухблочный ответ стоил бы вдвое;
- асинхронный вызов остаётся `done: false`, пока субагент работает. Конец решают два свидетеля, в
  порядке силы: уведомление в окне (называет вызов и статус) либо файл субагента, кончающийся его
  собственным текстом без вызова после (`idle`). Квитанция о запуске сама по себе конца не
  доказывает. `result` — «N tool calls», `resultText` — отчёт субагента;
- уведомление сохраняет вид `message`/`user`, но получает `title: task-notification` и
  `toolCallId` своего вызова — связь читается из полного текста ДО клипа, поэтому обрезка длинного
  отчёта её не рвёт;
- у каждого свёрнутого вызова (Claude и Codex) есть `doneAt` — время записи его `tool_result`.
  Без этого потребитель, считающий хронологию, знал начало вызова и не знал конца.

Файл субагента читается тем же парсером: `ccmux transcript <session> --agent <id>` и
`transcript.read { agent }` подставляют `subagents/agent-<id>.jsonl` вместо файла сессии; для
Codex ответ — `unavailable` со словами «this runtime keeps no agent transcripts». Факты субагента
кэшируются по mtime (`MtimeCache`): законченный файл больше не меняется, а спрашивают его на каждом
окне, содержащем вызов.

`--text-limit CHARS` (контроль: `textLimit` до 65 536) поднимает предел текста записи: клип по
умолчанию (6000) размечен под листинг, а не под отчёт, и потребителю, разбирающему уведомление или
показывающему длинный ответ целиком, нужен текст без обрыва.

## Чтение untyped-границы без `as`

Raw JSONL — внешняя нетипизированная граница (формат принадлежит агенту). Читается
через type-guards в `normalize.ts` (`isRecord`/`str`/`rec`/`num`/`flattenContent`) — это
разрешённое исключение «изолированный адаптер над untyped external», ноль `as`/кастов.

## Добавить новый агент

1. `src/agent/<agent>/` — реализовать `AgentProvider`.
2. Зарегистрировать provider в `src/agent/index.ts`.
3. Добавить значение в `AgentKindSchema` (`chat/identitySchema.ts`).
Ядро (`list`, `transcript`, TUI) не меняется — оно работает с контрактом.

## Codex lifecycle boundary

Codex provider реализует transactional first-rollout binding, resume, transcript, tokens и model
parsing. Pending generation живёт отдельно от ready Session и привязывается по exact persisted
launch marker; cwd/mtime никогда не выбирают rollout. Production boundary остаётся обычным
per-session Codex TUI под tmux; внешний App
Server не становится вторым driver или transcript source. Решение и probes:
`docs/decisions/2026-08-10-codex-process-tui-driver.md`.

## Кто отправил сообщение

Всё, что входит в разговор извне модели, провайдер записывает сообщением пользователя: набранное
человеком, письмо другой сессии, возврат хука, уведомление о фоновой задаче. Потребителю, который
действует по словам человека, нужно знать, что из этого отправил человек, и ответить может только
владелец истории: письма лежат в ledger ccmux, набранное им самим — в его журнале, а формы записей
харнеса читает его же разборщик. Реализация: `src/context/messageSender.ts`,
`src/context/exactMessage.ts`, `src/session/sentKeys.ts`.

`transcript --json` и `transcript --grep --json` несут у каждого сообщения пользователя управляемой
сессии поле `sender` — вердикт и причину:

| вердикт | что значит | по чему судится |
|---|---|---|
| `person` | введено в клиенте провайдера: набрано, вставлено, продиктовано, отправлено во время идущего хода | ни одно из условий ниже |
| `session-letter` | письмо другой сессии, доставленное ccmux | конверт `[chat from …` (в том числе внутри возврата Stop-хука) и его `id` есть в ledger этой машины |
| `routed-input` | ввод через router или приложение; автор — не подтверждённый человек | конверт `[input via …` / `[application input via …` и его `id` есть в ledger |
| `harness` | говорит харнес: возврат хука, уведомление о задаче, напоминание, вывод локальной команды | формы записей харнеса |
| `ccmux-keys` | набрано в панель командой `ccmux send` | отпечаток текста есть в журнале набранного для этой сессии, не раньше десяти минут до записи сообщения |
| `unverifiable` | читается как письмо или маршрутизированный ввод, но в ledger такого сообщения нет — либо текст прочитан обрезанным | — |

Вердикт — о том, кто отправил, а не кто написал слова: вставленный текст отправил тот, кто вставил.

`ccmux send` набирает текст клавишами, и в истории он неотличим от набранного человеком. Поэтому
каждая отправка оставляет строку в `sent-keys.jsonl` каталога состояния: сессия, отпечаток текста,
время и кто запускал команду. Текст не хранится — он уже лежит в разговоре. Граница названа в самой
причине вердикта `person`: клавиши, посланные в панель мимо ccmux, нигде не записаны и читаются так же.

Обрезанный текст потерял то, что различает отправителей, — id письма и отпечаток набранного, — поэтому
человеком он не называется никогда: вердикт `unverifiable`, а целое сообщение читается по id.

### Одно сообщение целиком

Сообщение цитируется другим системам своим `id`: id записи провайдера и часть записи,
`<запись>:<часть>`. Агент видит в собственной истории id записи, поэтому `transcript <сессия>
--message ID` принимает и его, и полный id. Ответ — `target`, `messageId`, `outcome`, `observedAt`
и `message` (`id`, `seq`, `recordedAt`, `text` целиком, `sender`). Исходы: `resolved`; `not-found`;
`not-user-input` — id называет ответ агента или вызов инструмента; `ambiguous` — в записи несколько
сообщений пользователя, нужен полный id; `too-large` — текст больше 256 КиБ и обрезанным не
отдаётся; `unsupported` — у рантайма нет файла истории; `unavailable`. Читаются только строки
файла, в которых встречается id записи. В таблице `--grep` колонка `ID` стоит рядом с `SEQ`.

Для нити вне ccmux тот же вопрос отвечает операция control-службы `external.message`.
