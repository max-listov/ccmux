# Ход, который не закончится

## Наблюдение (живое, с доказательствами)

Письмо с `--defer` не доставлялось получателю. `ccmux inbox` честно назвал причину:

```
↳ held: deferred — the recipient has not finished its turn yet
```

При этом сессия по всем видимым признакам **готова**: спиннер погашен, композер пуст, `list`
показывает `idle`, человек пишет в неё руками и получает ответ. Доставилось письмо только после
того, как человек вручную пингнул сессию.

Хвост беседы в этот момент:

```
09:22:26  role=user  [tool_result]      ← последняя запись
```

Ход был прерван на полуслове: тул отработал, результат записан, а завершающего текста **не будет
никогда** — этот ход мёртв.

## Корень

`src/chat/deliver.ts` → `deferReady`, три условия:

```ts
if (provider.scanPane(pane).state === "working") return false;   // 1. не работает
const lm = lastTranscriptMessage(s, m);
if (!(lm && lm.role === "assistant" && lm.kind === "message")) return false;  // 2. ход кончился ТЕКСТОМ
const mt = lastActivityMs(s, m);
return mt !== null && nowMs - mt >= DEFER_GRACE_MS;              // 3. тишина ≥ 6с
```

Условие (2) отделяет «ход завершён» от «пауза в середине хода» — и это правильно: беседа пишется
раздельными записями (thinking / text / tool_use), поэтому «последняя запись — текст ассистента»
случается и в середине хода.

Но **нигде не спрашивается, идёт ли ход вообще**. Прерванный ход неотличим от идущего: у обоих
последняя запись «оборвана на туле». Разница между ними — только время: живой ход двигает
транскрипт, мёртвый лежит неподвижно.

Итог: письмо ждёт события, которое не может наступить.

## Почему это не редкий случай

Так выглядит **любая** сессия, перезапущенная в момент работы, — а мы перезапускаем их пачками
(`restart --all` ровно для этого и сделан). То же самое даёт компактинг, пойманный посреди хода.

Второй пострадавший — **`ccmux wait`**: он использует ту же `deferReady`. Значит скрипт или агент,
ждущий такую сессию, простоит до таймаута (по умолчанию 300с) и получит exit 2 «ещё работает», хотя
она не работает вовсе.

## Кандидаты решения (валидаторам — разнести по плюсам/минусам)

**A. Порог тишины.** Считать ход завершённым, если пейн не работает И транскрипт неподвижен заметно
дольше обычного (порядка минуты). Плюс: не зависит от агента и от хуков, работает и для Codex.
Минус: эвристика по времени; надо не задеть длинный тул (его прикрывает признак «работает» в пейне,
но если скан пейна не сработал — прикрытия нет).

**B. Доверять lifecycle-хукам.** `SessionStart` пишет `idle` при запуске, `Stop` — при конце хода
(`src/agent/sessionStatus.ts`). После рестарта хук уже сказал «ход не идёт» — это событие, а не
догадка. Плюс: точно, без порогов. Минус: хуки есть только у Claude и только у сессий, запущенных с
ними; у Codex и у старых запусков файла нет.

**C. Комбинация A+B** с приоритетом события над таймаутом. Минус: три условия ИЛИ — риск, что
логика перестанет читаться.

**D. Что-то лучшее, чего я не вижу.** Ради этого и конвейер.

# Правки валидатора-1 (надёжность признака готовности)

**Вердикт: диагноз верен, но моя правка в задуманном виде ОПАСНА.**

1. **Окно загрузки уничтожает письмо.** После рестарта пейн уже «не работает», но ещё не
   отрисован (`ready:false`), транскрипт заморожен на оборванном ходе — порог тишины выполнен
   с нулевой секунды. Демон вставит текст в недорисованный интерфейс и **запишет ack**, а ack —
   источник правды дедупа: письмо помечено доставленным и не всплывёт никогда. *Неверный вердикт
   готовности не задерживает почту, он её уничтожает.* Бьёт ровно по той популяции, которую
   таска чинит. Лечится обязательным `scan.ready`.
2. **Запрос разрешения читается как idle** (`WORKING_RE` не содержит его маркеров). Для чата
   прикрыто гейтом `chatDeliverable`, для `wait` — **нет**: он получил бы «ход закончен» на
   сессии, ждущей нажатия человека. Скрипт поедет дальше по несделанной работе.
3. **Кандидат B в одиночку — новый вечный висяк**: при ESC-прерывании `Stop` не срабатывает и
   lifecycle навсегда `working`; а продолжение через `{decision:"block"}` оставляет `idle`
   посреди хода. B годится только как подтверждающий сигнал со сверкой свежести, не как гейт.
4. **Сессия без единого хода** держит отложенную почту вечно (нет транскрипта → оба условия
   ложны навсегда). Тот же класс, в плане не было.
5. **Мой довод «работает и для Codex» неверен**: у Codex нет `chatDeliverable`, чат его
   пропускает целиком; в `wait` его детектор сам себя объявляет некалиброванным.
6. **Числа из кода:** тик доставки 3с → 60с это ~20 независимых замеров пейна; вдесятеро больше
   внутриходового зазора (6с) и впятеро меньше таймаута `wait` (300с). **Ниже 30с нельзя** —
   это период `ensure`, до которого после форка беседы ccmux ещё смотрит в замороженный файл.
7. Комментарий в `stopHook.ts` о «temporally disjoint» перестаёт быть верным — поправить там же.
8. `deferReady` **не тестируем** (три файловых чтения) — именно поэтому баг и уехал.

# Правки валидатора-2 (потребители и честность диагностики)

**Вердикт: план недо-охвачен по `wait` и мис-охвачен по форме.**

1. **`wait` — не «второй пострадавший», а первоклассный потребитель, чей КОНТРАКТ меняется.**
   Он обещает «ход завершён добровольно» в четырёх местах (код, help, README, промпт). После
   правки exit 0 будет значить и «ход убит». Документированный следующий шаг —
   `transcript --last-message` — вернёт текст ДО прерванных тулколов, то есть устаревший отчёт
   с успешным кодом возврата. Код возврата оставить 0 (третий сломает скрипты), но **человеческая
   строка обязана различать два пути**.
2. **В `wait` уже живут два «ждём невозможного», к отложенной почте отношения не имеющие:**
   (а) `unreadFor` не фильтрует по `notBefore` — армированный роутером watchdog на 600с делает
   `wait` бесполезным на все 10 минут; (б) почта получателю с выключенным чатом не доставится
   никогда → `wait` висит до таймаута всегда. Чинить вместе — это одна болезнь.
3. **`wait` не перепроверяет живость в цикле** — на остановленной сессии печатает «still working
   after 300s»: две лжи в одной строке.
4. **Одна фраза удержания на три разных гейта** (`deliver.ts:179`) + вторая копия того же
   утверждения в `holdReason.ts:67`, которая ложна там, где хода нет вовсе: демон не запущен,
   письмо стоит за immediate-письмом, насыщение `MAX_PER_PASS`. И `pending` обещает «демон
   доставит за секунды», не зная, жив ли демон.
5. **Против «убрать, не добавить»:** кандидат C (три ИЛИ) — единственная форма, которая растит
   правило. Убирающая форма — перестать выводить «идёт ли ход» из ВИДА последней записи (прокси,
   который никогда не отвечал на нужный вопрос) и спросить пейн, который на это уже отвечает.
6. **Тесты должны утверждать `why`, а не только булев результат** — иначе тест не отличит фикс от
   «всегда готов». Плюс тест на неотрисованный пейн — именно он доказывает, что дыра закрыта.

# Пробники перед кодом (требование валидатора-2, §16)

- **Компактинг НЕ форкает беседу** — uuid в реестре, в пейне и в имени файла совпали, файл просто
  дорос. Значит механизм именно «мёртвый ход»; форк — отдельная опасность (переполнение контекста).
- **Транскрипт дописывается ПОСЛЕ старта** (mtime > штампа запуска) → кандидат E (штамп запуска как
  признак «ход не идёт») **отпадает**.
- `--last-message` на прерванном ходе вживую переснять уже нельзя — сессия ушла вперёд. Риск
  «устаревший отчёт с exit 0» принимаю как обоснованный и лечу формулировкой.

# Уточнённое решение

Ни «три ИЛИ», ни «выбросить условие». **Условие о виде последней записи ПОНИЖАЕТСЯ из гейта в
селектор порога** — оно перестаёт быть правом вето и становится мерой силы доказательства:

```
settled = !working && ready && !atMenu
          && quiet >= (последняя запись — текст ассистента ? 6с : 60с)
```

Одно выражение, два порога, ни одного ИЛИ. Ход, закончившийся словами, — сильное свидетельство,
хватает 6с. Оборванный ход — слабое, ждём минуту. Оба валидатора удовлетворены: предусловия
валидатора-1 на месте, правило валидатора-2 не выросло. Кандидат B не берём — он приносит два
новых вечных висяка (ESC и `{decision:"block"}`) ради экономии максимум минуты.

# Третий случай того же класса, найденный по ходу: подсказка ≠ ввод

Пока чинили прерванный ход, всплыл ещё один признак, который «выглядит убедительно, но говорит не
о том». Симптом тот же самый — письмо висит, `inbox` уверяет «a human is typing in that pane right
now», человека нет.

**Что в композере на самом деле.** Claude рисует собственную **подсказку-автодополнение** — как
автоподстановка в шелле. Мы читали пейн БЕЗ атрибутов, а в таком виде подсказка и набранный текст
это одна и та же строка после `❯`. Различить невозможно в принципе. Подсказка висит, пока её не
примут или не сбросят → доставка блокируется бессрочно.

**Эталоны, снятые с живых сессий (не предположение):**

```
пустой:     ❯
ввод:       ❯ настоящий ввод                ← без атрибутов
подсказка:  ❯ ESC[2mдоделай sp-blocksESC[0m  ← SGR 2 (dim)
```

**Фикс.** Пейн снимается с атрибутами (`capture-pane -e`) ОДНИМ вызовом; детектор композера получает
стилизованный текст, остальные детекторы — очищенный (`stripAnsi`). Лишних вызовов tmux нет.

Правило — **выбрасывать тусклые фрагменты и смотреть, осталось ли что-то**, а не «вся ли строка
тусклая». Это принципиально: набрал пару букв, Claude дописал остаток подсказкой — набранное
переживает фильтр и честно считается занятостью.

**Доказано на байтах из самого инцидента:** старый детектор говорит «ЗАНЯТ» и на подсказку, и на
ввод; новый — «свободен» на подсказку, «занят» на ввод.

**Урок, общий с основной таской:** признак, снятый не в том представлении, лжёт уверенно. Три раза
за день одна и та же фраза удержания оказывалась неправдой по трём разным причинам — и каждый раз
дело было не в фразе, а в том, что мы измеряли не то.
