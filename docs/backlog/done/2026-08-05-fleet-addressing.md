# Fleet-адресация (`machine:session`)

**Порядок: ТАСК 1 из 3.** Фундамент — два следующих таска (origin в сообщениях, наблюдаемость)
опираются на формат адреса, введённый здесь.

## Корень проблемы (из живого инцидента 2026-08-05)

> **В ccmux нет понятия «адрес агента во флоте». Есть только имя сессии, локальное для машины.**

Что случилось: агент машины A поручил задачу агенту машины B через
`ssh host-B 'ccmux restart agent-B2 --then "…доложи отчёт: ccmux msg agent-A"'`.
Агент машины B выполнил буквально — но `ccmux msg` внутримашинный, а на машине B оказался **однофамилец**
`agent-B` (тот же репозиторий, другая беседа). Отчёт лёг в inbox чужой прод-сессии; более
того, обнаружив там выключенный чат, агент машины B **включил его сам** — побочная мутация чужой сессии.

Ключевое: **ошибки не возникло нигде**. Команда отработала с exit 0, отправитель считает, что
доложил, заказчик молча ждёт. Тихий промах, а не громкий отказ.

Все следствия — из одного корня: имя неоднозначно за пределами машины, поэтому получатель
«достраивает» адрес сам и достраивает неверно.

## Дизайн

### Адрес
`<machine>:<session>` — напр. `host-a:agent-A`, `host-b:agent-B2`.
Голое `<session>` (без `:`) продолжает означать **локальную** сессию — существующее поведение
не меняется ни на йоту.

**Имя машины = `rcPrefix`** (например `host-a` / `host-b`) — не выдумываем второй идентификатор
машины, берём тот, что уже есть и уже виден в `ccmux list` (колонка RC).

### Реестр флота (конфиг)
Новая секция в `machine.json`:
```json
"fleet": { "host-a": "<ssh-alias-a>", "host-b": "<ssh-alias-b>" }
```
Значение — **ssh-алиас** (или `user@host`). Пусто/нет секции → кросс-машинная адресация
недоступна, всё работает как сегодня (чистая деградация, ноль регресса).

Своя машина в реестре может присутствовать — адрес `<своя>:name` разрешается **локально**, без ssh.

### Транспорт
`ssh <alias> 'ccmux msg <session> …'` — enqueue на стороне ПОЛУЧАТЕЛЯ (его демон доставляет как
обычно, со всеми существующими гарантиями: меню-гейт, typing-гейт, defer, ack-log).
Никакого нового протокола и никакого второго ledger — переиспользуем то, что уже работает.

### Что использует адрес
- `ccmux msg <machine>:<session> …` — главный кейс.
- `ccmux wait <machine>:<session>`, `ccmux transcript <machine>:<session> --last-message` —
  чтобы pull-модель (инициатор сам забирает отчёт) стала однострочной без ручного ssh.
- `ccmux restart <machine>:<session> [--then …]` — постановка задачи на другую машину.

### Честная деградация (обязательное требование)
Транзит сервер→сервер существует только пока владелец подключён (серверных ключей нет by design —
это осознанная модель безопасности флота). Поэтому:
- ssh не прошёл → **явная ошибка с понятным текстом** и ненулевой exit code. Никакого «молча
  проглотили». Сообщение при этом фиксируется в исходящем логе (таск 3), чтобы отправитель видел,
  что не ушло.
- Ретраи/очередь исходящих — **НЕ в этом таске** (переусложнение для v1); при нужде отдельно.

### Развилка на решение Max
**Спуфинг отправителя.** Локально отправитель неспуфаем (берётся из `CCMUX_SESSION`). При ssh-транзите
получатель видит `cli` — то есть кросс-машинное сообщение придёт без честного «от кого», если не
передать origin явно (это делает **таск 2**). Передача origin флагом означает: тот, у кого есть ssh
на машину, может назваться кем угодно. Моя позиция: **приемлемо** — у кого есть ssh, тот и так может
всё (запустить `ccmux msg` от любого имени, править реестр); граница доверия здесь — ssh-доступ,
и она не меняется. Нужен твой «ок» на эту формулировку.
