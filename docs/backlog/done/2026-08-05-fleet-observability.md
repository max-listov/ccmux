# Наблюдаемость кросс-машинного обмена

**Порядок: ТАСК 3 из 3.** Опирается на адрес (таск 1) и `fromMachine` (таск 2).

## Проблема — на прямой вопрос Max «что не так с логами, почему мы этого не видим»

Разбор инцидента 2026-08-05 показал: **промах был структурно невидим**.

- **У инициатора (машина A) нет ни следа.** Задача ушла через `ssh … 'ccmux restart --then'` — это не чат,
  в ledger не попадает. Инициатор не имеет записи, что он вообще что-то поручил.
- **У исполнителя (машина B) запись есть** (`agent-B2 → agent-B`), но она локальная,
  и смотреть в неё некому.
- **Ошибки не было**: exit 0, «доставлено». Один ждёт молча, другой отчитался не туда.
- **Нет ни одного места, где виден обмен целиком.** Каждый ledger — свой мирок; чтобы понять,
  что произошло, пришлось руками лазить по двум машинам и сопоставлять транскрипты.

То есть дело не в «мало логов» — логи есть. Дело в том, что **нет флотового среза**: ни адреса
(таск 1), ни записи у инициатора, ни общего взгляда.

## Дизайн

1. **Исходящая запись у инициатора.** Кросс-машинная отправка (`msg`, `restart --then`) пишет в
   локальный ledger запись об ИСХОДЯЩЕМ (кому, на какую машину, что, результат транзита). Тогда
   «я поручил и жду» — факт в логе, а не в чьей-то голове. Провал ssh тоже пишется (видно, что не ушло).
2. **`ccmux fleet`** — обзор всего флота одной командой: сессии всех машин из `fleet`-реестра
   (name, machine, model, state, uptime), `--json` для потребителей. Это же **закрывает мину
   однофамильцев**: сразу видно, что `agent-A` живёт на host-a, а на host-b есть похожий `agent-B`.
   Реализация — параллельный `ssh <alias> 'ccmux list --json'`; недоступная машина показывается как
   недоступная, а не роняет вывод.
3. **`ccmux chat log --fleet`** — свести ledger'ы машин в один хронологический поток (по ts),
   с колонкой машины. Именно то, чего не хватило при разборе.
4. **Диагностика доставки.** Сейчас причина холда видна только в логе демона (`grep` по
   `~/.ccmux/ccmux.log`). Показывать её там, где смотрят: в `ccmux inbox` — почему сообщение ещё
   не доставлено («human is typing» / «at a menu» / «target not running» / «chat off у получателя»).
   Прямо этот случай: у `agent-B` **чат был выключен**, и это выяснилось только тем, что
   агент полез включать его сам.

## Acceptance
- [x] Кросс-машинная отправка пишет исходящую запись у инициатора (вкл. неуспех транзита) — `src/fleet/outbox.ts`, пишут и `msg`, и `restart --then`. Отдельный файл, а не общий ledger: исходящая запись, адресованная `agent-b`, попала бы в локальный цикл доставки (он матчит по `to`) и была бы вставлена ОДНОИМЁННОЙ локальной сессии — ровно тот баг, который таск и убирает.
- [x] `ccmux fleet [--json]` — сессии всех машин реестра, каждая строка сразу готовый адрес; недоступная машина помечена, вывод не падает, exit 0.
- [x] `ccmux chat log --fleet` — слитый по времени поток с колонкой машины; `--json` теперь **уважает `--fleet`** (раньше молча отдавал одну машину — валидатор), форма ответа одна на оба случая, эмитится через ту же схему, что её парсит.
- [x] `ccmux inbox` называет причину. По итогам валидации добавлены два реальных гейта, которые молчали: получатель, чей агент вообще не умеет принимать чат (постоянный, не «через пару секунд» — теперь и `msg` отказывает на входе), и rate-limit. Причина привязана к КОНКРЕТНОМУ сообщению (`msgId`), иначе одна запись демона штамповалась под всеми письмами получателя.
- [x] Параллельный опрос машин с таймаутом — `Promise.all` + 20с, `armTimeout` реально убивает ssh.
- [x] `help` + README; тесты на слияние/сортировку/пометку недоступных, на outbox (round-trip, отдельный файл, битая строка, best-effort) — чистые функции, без ssh.
