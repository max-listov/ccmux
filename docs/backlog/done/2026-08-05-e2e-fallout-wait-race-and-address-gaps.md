# Две находки живого прогона 0.6.0

Обе всплыли в кросс-машинном e2e между двумя сессиями на разных машинах — не в теории.

## 1. `wait` сразу после `msg` — гонка

**Что видели.** Отправил письмо, тут же `ccmux wait <адрес>` — вернулся **за 0.7 секунды**
с «turn finished». Хода не было вовсе: демон доставляет письмо следующим тиком, а до этого
получатель честно idle, и `deferReady` совершенно правильно говорит «сидит спокойно».

**Почему это важнее обычного бага.** Ровно этот рецепт (`msg` → `wait` → `transcript
--last-message`) мы только что вписали в промпт агентам как правильную замену самописным
циклам. То есть рекомендованный путь обгонял сам себя, а агент получал ответ от **предыдущего**
хода и считал задачу выполненной.

**Корень.** «Ход закончился» — свойство ПОЛУЧАТЕЛЯ, а вопрос задавался про РАБОТУ, которую
ему только что отправили. Пока работа не доставлена, простаивающий пейн — не ответ.

**Фикс.** `wait` не считает сессию успокоившейся, пока для неё есть недоставленная почта.
Проверяется на каждом опросе (письмо может прийти в середине ожидания), через тот же
`unreadFor` + ack-log, что использует `inbox`. Чат при этом остаётся необязательным: нет
ledger'а — нет и влияния.

## 2. Fleet-адрес понимали не все глаголы

**Что видели.** Первое же действие подготовки — `ccmux chat on host-b:agent-b` — ответило
`no such session: host-b:agent-b` (exit 1, громко, но по существу отказ). Пришлось идти через
голый `ssh`. Позже в транскрипте тестового агента обнаружилось, что он **сделал ровно то же
самое** самостоятельно: `ssh <host-b> 'ccmux inbox agent-b --peek'` — потому что `inbox`
адрес тоже не принимал.

Это та самая «несогласованность», из-за которой пользователь (человек или агент) перестаёт
доверять правилу «адрес работает везде» и возвращается к обёрткам, которые мы и убирали.

**Фикс.** Адрес принимают `chat on|off`, `router on|off`, `inbox`. Для них потребовалась одна
новая деталь: у этих команд под-глагол стоит ПЕРЕД именем (`chat on <name>`), поэтому
форвардер получил `verbArgs` — иначе на той стороне пересобиралась бы другая команда
(`chat <name> on`).

Граница осталась прежней и осмысленной: адрес принимает всё, что оперирует СУЩЕСТВУЮЩЕЙ
сессией; создающие (`new`, `adopt`) — локальные по природе.

## Acceptance
- [x] `wait` не рапортует «finished», пока получателю есть что доставить — `pendingInbound(...).length === 0 && deferReady(...)`.
- [x] Проверка внутри цикла опроса, а не единожды на входе: письмо может прийти в середине ожидания.
- [x] Отсутствие/нечитаемость ledger'а не ломает обычный `wait` — чтение обёрнуто, чат остаётся необязательным.
- [x] `chat on|off`, `router on|off`, `inbox` принимают `<machine>:<session>`.
- [x] Под-глагол не переставляется при пересылке — `verbArgs` в `ForwardOpts`, тест на реальной строке сборки argv.
- [x] README перечисляет адресуемые глаголы полностью; `help` у `chat`/`inbox` показывает `machine:name`.
- [x] `bun run check` зелёный — 287 pass.

## Что НЕ делаем
Не добавляем `msg --wait` (отдельный флаг там, где уже есть отдельная команда). Не делаем
адресуемыми `new`/`adopt`.

### Почему это стоило отдельного захода
Оба дефекта нашлись только потому, что прогон был **живой и нативный**: агенту не давали
команд, и он повёл себя как реальный пользователь — упёрся в ту же стену, что и я, и обошёл её
голым ssh. Синтетический тест по написанному сценарию не поймал бы ни того, ни другого.
