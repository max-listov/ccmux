# Снимок сессии говорит, когда начался идущий ход

## Зачем

Потребитель, рисующий живое состояние сессий, хочет показывать рядом с `working` растущий
счётчик: сколько уже длится текущий ход. Сегодня этот ответ вывести неоткуда.

Что есть:

| источник | про длительность хода |
|---|---|
| `events` → `turn-start` | момент начала — но только если слушал в этот момент |
| `events` → `turn-end` | `durationMs` уже **законченного** хода |
| `list --json`, `fleet --json` | `state: "working"`, `uptime` сессии — про ход ничего |

Отсюда две дыры, и обе не лечатся на стороне потребителя.

**Поток даёт переходы, а «сколько идёт этот ход» — это состояние.** Потребитель, поднявшийся
только что, видит `working` и не может сказать, идёт он три секунды или сорок минут: начало
осталось в прошлом, а следующее событие по этой сессии будет уже `turn-end`. Перезапуск
потребителя — обычное дело, а не авария, и после него состояние должно читаться целиком.

**Удалённые машины.** Состав их сессий доступен через `fleet --json`, и это единственный
источник, который до них дотягивается одним вызовом. Слушать события каждой машины ради одного
числа — несоразмерно тому, что нужно.

## Результат

- У сессии в `list --json` и `fleet --json` есть момент начала текущего хода.
- Поле пустое (или отсутствует), когда сессия не в ходу — «неизвестно» и «не идёт» различимы.
- Потребитель считает длительность сам и тикает её локально; ни опроса, ни подписки ради
  счётчика не заводится.

## Форма

Предлагается `turnStartedAt` — **абсолютный** ISO-момент, рядом с существующим `state`:

```jsonc
{ "name": "…", "state": "working", "turnStartedAt": "2026-08-25T07:41:12.004Z" }
```

⚠️ **Абсолютный момент, а не «прошло N миллисекунд».** Elapsed протухает в дороге: у снимка,
который шёл через сеть и полежал в кэше потребителя, счётчик окажется занижен ровно на время
доставки, и разойдётся тем сильнее, чем реже потребитель обновляется. Абсолютный момент такого
дефекта не имеет — он одинаково верен в любой момент чтения.

Имя поля — на усмотрение владельца; важна абсолютность и присутствие в ОБОИХ снимках, включая
`fleet`, иначе удалённые сессии останутся без ответа.

## Подсказка по месту

Значение, судя по всему, уже существует внутри: `src/events/observe.ts` держит `turnState`, а
`src/commands/hookStatus.ts` берёт длительность `turn-end` из предыдущего штампа — то есть момент
начала где-то записан. Тогда задача не «завести факт», а показать его в снимке.

## Что мешает просто показать штамп

Момент действительно записан — в `working`-штампе lifecycle-файла. Но этот штамп **никто не
закрывает, кроме хука `Stop`, а `Stop` срабатывает не всегда**: замер на живой машине показал 7
сессий со штампом `working`, из них 4 — осиротевшие, самому старому 2.5 суток. Все четыре по
`turnState` уже `settled` (`turn-ended`), то есть ход давно закончился словами агента, а хук о
нём не сказал.

Одного этого мало, чтобы соврать в снимке: `resolveLiveState` решает по пейну, и такая сессия
показывается `idle`. Ложь появляется на СЛЕДУЮЩЕМ ходе. `lifecycleToWrite` намеренно не двигает
начало хода вперёд, когда промпт приходит внутрь идущего хода, — и осиротевший штамп неотличим
от идущего хода, поэтому новый ход наследует чужое начало. Тогда снимок покажет ровно то, что
acceptance запрещает: момент прошлого хода.

Тот же корень портит и поток: осиротевший ход не получает `turn-end` вовсе, а следующий за ним
не получает `turn-start` (хук считает, что ход уже идёт). Потребитель остаётся с сессией,
которая для него навсегда «работает».

Поэтому задача — не только показать факт, но и сделать его верным: штамп `working` должен
означать идущий ход, а не «когда-то начался».
