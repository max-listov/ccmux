# Reply-подсказка чата говорит «no route back», хотя wire-маршрут существует и работает

## Зачем

Воспроизведённый случай (2026-08-25). Сессия на hub-машине (`<hub>`) отправила `ccmux msg` сессии на
сервере (`<server>`). Входящий тег на приёмной стороне получил вид:

```
[chat from ccmux/claude@<hub>:<session>#<uuid> · task: … · no route back to <hub> from here —
answer with ccmux msg owner "<your reply>"]
```

Агент-получатель по правилам обязан использовать pinned reply-команду — и корректно ответил
owner'у вместо отправителя. Ответ агента ушёл человеку, межагентский диалог разорвался.

При этом маршрут назад существовал и работал в ту же минуту, проверено:

- `machine.json` сервера: `wire.peers: ["<hub>"]`;
- `stitchwire doctor` на обеих сторонах: агенты 0.10.1, protocol v2, оба брокера connected,
  `<hub>` в ростере `serving`;
- решающий пробник: `ccmux msg <hub>:<session> …` с сервера доставлен на hub мгновенно
  (`accepted`, сообщение получено).

То есть «no route back» — ложное отрицание в момент вычисления reply-подсказки, а не факт о
транспорте. Ущерб именно от подсказки: она **предписывающая** (получатель обязан ей следовать),
поэтому ложный вердикт гарантированно уводит ответ не туда — тихо, без ошибки на любой стороне.

## Гипотеза (проверить по коду)

Reply-hint, похоже, вычисляется из канала прибытия (envelope приехал по ssh-хопу hub→server;
обратного ssh server→hub нет by design) и не консультируется с `wire.peers`/локальным агентом —
либо консультируется способом, дающим ложный отказ (таймаут пробы, кэш прежнего состояния,
проверка до подключения агента).

## Результат

- Reply-подсказка строится из того же резолвера маршрута, которым `msg` реально доставляет:
  если `ccmux msg <hub>:<session>` с этой машины прошёл бы — подсказка обязана дать именно его.
- Fallback «answer with msg owner» остаётся только для действительно недостижимого отправителя,
  и тогда тег называет причину недостижимости (peer offline / wire down), а не голое «no route».
- Регрессия: доставка hub→server при живом wire даёт reply-команду на отправителя; при
  остановленном локальном агенте — честный fallback с причиной.

## Acceptance

- [x] На сервере с `wire.peers: [<hub>]` и живым агентом входящий тег от hub-сессии несёт
      `reply: ccmux msg <hub>:<session> …`, не `msg owner`.
- [x] Ложный «no route back» невоспроизводим при живом wire; при мёртвом — fallback называет
      причину.

## Что сделано

Гипотеза подтвердилась по коду: reply-подсказка вычислялась двумя копиями одного выражения
(`src/chat/deliver.ts`, `src/commands/stopHook.ts`) как «отправитель — это мы, либо он есть в
`fleet`». Консультировалась только ssh-карта; `wire.peers` — транспорт, существующий ровно для
машин, которые ssh адресовать не может, — в вычислении не участвовал вообще. Никакого таймаута,
кэша или гонки: направление, живущее только на wire, было недостижимым по построению.

- `src/chat/replyRoute.ts` (новый) — `replyRouteFor` / `replyRouteToSender`: вердикт строится тем же
  резолвером, которым `msg` реально доставляет (`routeFor`), поэтому оба транспорта учтены и второй
  карты маршрутов, способной разойтись с первой, больше нет. Возвращает не boolean, а
  `{ replyable: true } | { replyable: false, reason }` — подсказка предписывающая, и голый вердикт
  читателю нечем проверить.
- Сверх маршрута проверяется ровно одно: локальный конец wire (наличие сокета агента). `msg`
  резолвит точного удалённого пира ДО постановки в outbox, поэтому без сокета reply-команда упала бы
  с exit 1, а не встала в очередь. Проверка — только существование файла, никогда не проба: код
  работает на частоте доставки демона, и вопрос с таймаутом отвечал бы «недостижим» для живого, но
  занятого агента — то же ложное отрицание на новом месте. Живость дальней стороны не спрашивается:
  на неё честно отвечает сам хоп (queued, retried).
- `src/chat/format.ts` — `opts.replyable: boolean` → `opts.reply: ReplyRoute`; fallback теперь
  `cannot reach <machine> from here (<причина>) — answer with ccmux msg owner …`. `undefined`
  по-прежнему молчит (Telegram-зеркало и другие рендереры не знают ничьей таблицы маршрутов).
- `src/chat/deliver.ts`, `src/commands/stopHook.ts` — оба канала зовут один `replyRouteToSender`,
  так что тег не может разойтись между демоном и Stop-hook'ом.
- `test/reply-route.test.ts` (новый, 8 тестов) — wire-пир с живым агентом replyable без всякой
  ssh-карты; мёртвый агент → fallback с точным путём сокета в причине; wire выигрывает у ssh-алиаса,
  как и в `runPeer`; ssh-пир и сама машина replyable; неизвестная машина отказана причиной
  резолвера; `cli`-отправитель не получает вердикта вовсе; сквозной рендер тега.
  `test/fleet-address.test.ts` обновлён под новую сигнатуру и новую формулировку fallback.
- `docs/architecture/peer-routing.md` — раздел «The reply hint is the resolver's answer, not a second
  map»: почему подсказка предписывающая, почему один резолвер, почему существование сокета, а не
  проба, и почему fallback обязан называть причину. `CHANGELOG.md` — запись в `[Unreleased]`.

Проверено: `tsc --noEmit` чисто, `bun test` — 487 pass / 0 fail. Реальный пробник на этой машине
(read-only, конфиг сервера воспроизведён в памяти): при живом сокете тег несёт
`reply: ccmux msg <hub>:<session> --to-agent claude --to-thread … --task …`, при мёртвом —
`cannot reach <hub> from here (the stitchwire agent is not running here — no socket at …) — answer
with ccmux msg owner …`. Релиз и коммит не делались.
