# Окружение сессии — объявленный рецепт

## Откуда

Предыдущая записка закрыта Шагом 1: неявное наследование `.env` рабочей папки стало **видимым** —
причина `env` в колонке `RESTART`, происхождение и имена переменных в `doctor`. Само поведение при
этом не изменилось, и это осознанно: записка предписывала сначала замерить флот.

## Замер, ради которого ждали

`ccmux doctor` на машине владельца, 2026-08-25:

```
env:    PROBLEM — 5 session(s) are handed variables from an env file in their own directory, undeclared
        <session> — 23 name(s) from <dir>/.env
        <session> — 30 name(s) from <dir>/.env
        …
```

**5 из 14 сессий** живут на унаследованных переменных: от 1 до 30 имён, среди них ключи внешних API
и OAuth-секреты. Каждая такая переменная лежит в окружении агента **и каждого процесса, который агент
порождает** — MCP-серверов, шелл-тулов, сабагентов.

Это и есть ответ на вопрос «можно ли просто выключить». **Нельзя:** одна из этих пяти — ровно тот
случай, с которого началась исходная записка (MCP-сервер проекта подключается только потому, что ключ
пришёл из `.env` через окружение). Выключение наследования сегодня воспроизведёт тот отказ сразу на
пяти сессиях.

## Что делаем

Порядок из исходной записки, шаги 2 и 3, без изменений по существу:

- Поле **`envFile`** в записи сессии (nullable), относительный путь резолвится от `dir`.
- `launchEnv` перестаёт слепо копировать `process.env` и собирает окружение по объявленному рецепту:
  явная база (`PATH`, `HOME`, `LANG`, `TERM`, `SSH_AUTH_SOCK`, …) из конфига машины + объявленный
  env-файл. Файл **побеждает** унаследованное — иначе детерминизма нет (сегодня приоритет обратный:
  рантайм не перетирает уже заданное).
- Поверхность: `ccmux new <name> <dir> --env-file <path>` и `ccmux env-file <name> <path>`
  (как `chat on` / `mode` — применяется на рестарте, о чём команда и сообщает).
- Файла нет на старте — **поднимать и кричать**, а не падать: сессия, которая не встаёт, для
  супервизора хуже, чем сессия без переменной.

### Развилка «как погасить автозагрузку Bun» — РЕШЕНА пробником

Ни один из трёх кандидатов записки не понадобился. У рантайма есть штатный флаг — `--no-env-file`
(документация Bun, раздел «Disabling automatic `.env` loading»), и он делает ровно то, что нужно.
Проверено на Bun 1.3.14:

```
-- default:                                PROBE_SECRET = "leaked-from-dotenv"
-- --no-env-file:                          PROBE_SECRET = undefined
-- --no-env-file --env-file=declared.env:  DECLARED = "yes" | PROBE_SECRET = undefined
```

**Но одного флага мало, и это тоже пробник, а не теория.** Скомпилированный бинарь
(`bun build --compile`) флаг НЕ видит — он попадает в argv приложения, а не рантайма, и `.env`
всё равно подхватывается:

```
-- compiled, default:            PROBE_SECRET = "leaked-from-dotenv"
-- compiled with --no-env-file:  PROBE_SECRET = "leaked-from-dotenv"
```

Проверены и отвергнуты как замена: `BUN_ENV_FILE=`, `BUN_NO_ENV_FILE=1`, `BUN_CONFIG_ENV=false`,
`DOTENV_DISABLE=1` и `bunfig.toml` рядом с бинарём — ни один не гасит подгрузку в compiled-режиме.

Поэтому механизмов **два**, и они падают в разных местах:

1. пейн запускается как `bun --no-env-file <entry> _run <name>` — секреты вообще не попадают в
   супервизор (рабочая форма прода);
2. рецепт **вычитает те же имена** при сборке окружения агента — гарантия не зависит от того, чтит
   ли флаг конкретная форма сборки.

Вычитание по именам приблизительно ровно в одном случае: переменная, которая есть и в `.env` папки,
и по-настоящему в окружении супервизора, будет убрана тоже. Это безопасная сторона ошибки —
отсутствующая переменная видна и лечится объявлением, утёкший секрет не виден и не лечится, — а
механизм 1 делает этот случай недостижимым в проде.

### Почему ccmux парсит объявленный файл сам, а не отдаёт его `--env-file`

Потому что `--env-file` кладёт переменные файла в **супервизор**, и тогда `.env` проекта смог бы
задать `CCMUX_STATE_DIR` и увести весь инстанс. Свой парсер держит досягаемость файла там, где её
объявили — у агента, — и делает рецепт свойством ccmux, а не того рантайма, который его хостит. Это
ровно исходная претензия записки: деталь реализации протекла в поведение продукта.

## Миграция — обязательная часть, а не приложение

Пять живых сессий сегодня работают на унаследованном. План обязан включать:

- пройти по списку из `doctor` и объявить `envFile` там, где переменные действительно нужны;
- только потом выключать неявную подгрузку;
- после выключения — `doctor` обязан показывать, что унаследованных не осталось (та же секция
  становится пустой, и это проверяемый признак завершённой миграции).

## Чего НЕ делать

- **Никакого автопоиска `.env`.** Только явный опт-ин.
- Не заводить «ещё один способ задать переменные» рядом с существующими: источник окружения должен
  быть один и объявленный.
- Не выключать наследование раньше, чем миграция пройдена, — иначе это тот же отказ, только на пяти
  сессиях сразу.

## Что сделано (2026-08-25)

- `src/agent/sessionEnv.ts` (новый) — парсер env-файла (кавычки одинарные/двойные/backtick,
  `export`, комментарии, многострочные значения, `$VAR`/`${VAR}` expansion; одинарные кавычки не
  расширяются) и сборка окружения по рецепту: унаследованное **минус** имена из env-файлов рабочей
  папки **плюс** объявленный файл, который побеждает.
- `CCMUX_*` и chat-credential из файла **отклоняются** и логируются: сессия даёт проекту переменные,
  а не право перенастроить супервизор. Проверено: `CCMUX_STATE_DIR=/tmp/hijacked` в файле не
  применяется, остальная часть файла применяется.
- `src/env.ts` — `withNoEnvFile` + `SELF_ARGV_NO_ENV_FILE`; пейны `_run` и `_bootstrap` запускаются
  с флагом.
- `envFile` в `SessionSchema`; `setSessionEnvFile`; `ccmux env-file <name> <path|--none>`;
  `ccmux new --env-file`; `ccmux env-file --adopt [--dry-run]`.
- `envInput` теперь дайджестит **объявленный** файл. Побочный эффект честный и полезный: у сессии,
  запущенной старым кодом, штамп разойдётся с новым расчётом → колонка покажет `env`, и это правда —
  рестарт действительно изменит её окружение.
- `inheritsUndeclaredEnv` — один предикат для `doctor` и `--adopt`, чтобы отчёт и лечение не
  разошлись. Он же чинит дефект первой версии проверки: сессии со штампом **до** появления поля
  `inputs` выпадали из списка миграции — то есть список читался пустым ровно на том флоте, которому
  он был нужен. Отсутствие карты `inputs` в штампе и есть доказательство, что сессию запускала
  сборка, которая ещё наследовала.
- `list --json` несёт `envFile: {path, present}`; человеческий `list` печатает строку про
  объявленный, но отсутствующий файл; `doctor` разделяет «объявлено» и «ещё наследует» и называет
  команду лечения.
- `test/session-env.test.ts` (14 тестов), доки: `docs/architecture/launch-recipe.md`, README,
  CHANGELOG.

Живая проверка на изолированном инстансе: объявление, предупреждение об отсутствующем файле, строка
в `list`, очистка поля. Проверка рецепта на реальных файлах: необъявленный `.env` не доходит до
агента (`removed: [PROJECT_SECRET, SHARED]`), настоящие переменные окружения сохранены, объявленный
файл применяется с expansion и многострочными значениями.

**Флот не тронут.** `ccmux doctor` показывает 5 сессий, которые ещё наследуют; `env-file --adopt
--dry-run` показывает, что именно будет объявлено. Ни `--adopt` без `--dry-run`, ни рестартов я не
делал — это решение владельца, и до него сессии продолжают работать ровно как раньше.
